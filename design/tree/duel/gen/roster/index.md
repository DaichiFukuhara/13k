## 親からの振り分け

- **責任**: 生成の手順を回し、ラン全体の確定した定義を組み立てる
- **詳細化の対象**: 親の本文1の機能「手順を回して組み立てる」。`gen` の解決法5層のうち
  5（フォールバック）。根の 1.6（主色は最も危険度へ寄与した特性から決まる）、
  1.8 のうち体数・出現順・体ごとの予算
- **継承する制約**: 根12件＋`duel` 4件＋`gen` 3件。とくに
  **「生成は決定論的」「検査を通らない技は必ず捨てる」
  「フォールバック技は検査を必ず通る固定値」「乱数系列を持つのは `roster` だけ」**。
  技の表現9要素（`gen` の親に残すもの4）。ラン全体を1つのシードから決める。
  容量の目安 **1,700 inlined bytes**
- **割り当てられた受け入れ条件**: 決定論（主）、停止性（主）、形状と外見の網羅（主）、
  公平性A・B（不合格を捨てる実行責任）
- **uses_seams**: `g2.move-result`, `g4.audit-verdict`
- **提供する seam**: `g1.move-request` / `g3.audit-request`（兄弟へ）、
  **`d1.run-definition`**（`gen` の代表として `duel` の `seam_inbox` 経由で `fight` へ）
- **parent_decision_ref**: `gen@2026-09-04-decision-1` ＋ `gen@2026-09-04-split-1`

## 1. これは何を決めるものか

**入力**: シード（32bit 整数）1つだけ
**出力**: `d1.run-definition` — ラン全体を最後まで走らせるために必要な確定済み定義すべて

**`roster` は `gen` の3子で唯一、状態と乱数系列を持つ。**

### 1.1 ラン全体を一度に作る

```
シード ──► ボス0（tier 0）──┐
      ──► ボス1（tier 1）──┼──► d1.run-definition ──► fight
      ──► ボス2（tier 2）──┘
```

**1体ずつではない。**`fight` が「次を作れ」と言う必要が無くなり、
**`fight → gen` の逆向きが原理的に生まれない**（`duel-split-2` の変更1）。

**成立する理由は根の 1.8 にある** — 「難易度は**敵側の危険度予算だけ**で上げる
（プレイヤー側の成長で上げない）」。
**N 体目の予算はシードとボス番号だけで決まり、戦績に依存しない。**
`fight` の結果を待つ理由がそもそも無い。

### 1.2 ボス1体を組み立てる手順（8段）

| # | 段 | 中身 |
| --- | --- | --- |
| 1 | **乱数列を作る** | シードとボス番号から専用の系列を導出する。**これ1本だけを使う** |
| 2 | **役割枠を決める** | `[突き, 横薙ぎ, 接近/遠距離, 範囲制圧, 固有技]`（1体目は4枠） |
| 3 | **各枠を数値化** | `g1` で `move` へ要求し、`g2` で受ける |
| 4 | **検査へ出す** | `g3` で `audit` へ。**不合格なら捨てて 3 からやり直す（最大8回）** |
| 5 | **上限超過ならフォールバック** | 検査を必ず通る**固定の技**（黄を持たない短射程の単発）を採用 |
| 6 | **セットの後処理** | GAP 枠の圧力・反撃窓の確保・高速技の抑制。**そのつど再検査する** |
| 7 | **外見を決める** | 実際に出た特性候補から主色を選ぶ（根の 1.6） |
| 8 | **HP・体勢・山札の材料を付ける** | `tier` ごとの値 |

### 1.3 セットの後処理（実装から）

| 処理 | 内容 |
| --- | --- |
| **GAP 枠の圧力** | 3番目が突進でなければ射程を4へ上げ、超過分を硬直 → 予備動作 → 威力の順で返す |
| **反撃窓の確保** | 硬直 ≥50F の技が2つ未満なら、**最も危険度の高い技**を選んで硬直を延ばす |
| **高速技の抑制** | 24F 技が2つ目以降なら 36F へ落とし、下がった危険度を威力 → 射程 → 硬直で戻す |

**出所は実装**（`generateBoss` の `open()` と `fast` の処理）。
[`design/AS_BUILT.md`](../../../../AS_BUILT.md) §5。

> ⚠️ **後処理は技を書き換えるので、そのつど `audit` へ出し直す。**
> 実装は後処理のあとに `validateBoss` を通しているが、
> **A（安全席）と B（回答2つ）が入ると、後処理で不合格へ落ちうる。**
> 実装には無い経路である（7-2）。

### 1.4 外見（根の 1.6 の実効化）

**主色はランダム装飾ではなく、実際に生成された特徴から選ぶ。**

| 候補になる条件 | 色 |
| --- | --- |
| 威力3以上の技がある | 赤（高威力） |
| 持続が最大の技がある | 橙（長い攻撃判定・残留） |
| 予備動作2以下の技がある | 黄（短い予備動作） |
| 防御能力を持つ | 緑 |
| 射程4の技がある | 青（長射程） |
| 追尾を持つ技がある | 藍 |
| 多段の技がある | 紫 |

**候補が空なら赤。**武器シルエットは固有技の形状から決まる。
**見た目が生成結果の関数になっている**ので、色は飾りではなく読める情報になる。

### 1.5 `tier` ごとの値（実装から）

| `tier` | 技数 | HP | 体勢 | 防御能力 |
| ---: | ---: | ---: | ---: | --- |
| 0 | 4 | 120 | 24 | **なし**（常に0） |
| 1 | 5 | 160 | 32 | 1〜3 から抽選 |
| 2 | 5 | 210 | 42 | 1〜3 から抽選 ＋ **第2形態変異** |

### 1.6 決定論の規約

- 乱数は**シードから導出した1本の系列**だけ。時刻・端末・実行回数に依存しない
- **引き直しは乱数の状態を進める。**それも含めてシードから再現できる
- **見た目の乱数（火花・画面揺れ）とは別系統。**
  実装は生成に `seeded()`（Mulberry32）、演出に `Math.random()` を使い分けている。
  **見た目の乱数を何回呼んでも次のリトライのボス構成は変わらない**
- **リトライ時は生成をやり直さない。**`fight` が `d1` を保持する（`fight` の責任）

## 2. なぜ要るのか

**引き直しのループを、どこかが持たなければならない。**
`move` に持たせると生成器が自分の検査結果を見ることになり、
`audit` に持たせると検査器が技を書き換えることになる（`gen` の不変条件9 違反）。

**`roster` をハブにすると、`move` と `audit` の間に線が1本も無くなる。**
親（`duel`）が5子案を却下した理由（検査器と生成器の間に引き直しのループが通る）は、
これで消える。

**停止性もここが持つ。**上限8回とフォールバックが無いと、
**特定のシードで生成が終わらない可能性がある。**

## 3. 誰が使い、誰が影響を受けるか

- **`fight`**: `d1.run-definition` を受け取る唯一の相手
- **`move` / `audit`**: `roster` から呼ばれるだけ。互いを知らない
- **`read`**（親経由）: 外見（主色・武器シルエット・緑の輪郭）は `roster` が決める。
  根の 1.1「姿から性格を推測する」がここに乗っている
- **プレイヤー**: 生成の待ち時間を体感する

## 4. 終わったとどうやって分かるか（受け入れ条件）

- [ ] **決定論**: 同一シードから2回作った**ラン全体**がバイト一致する。
      判定: 1,000 シードで2回ずつ生成し、シリアライズして全一致。
      **実装済みの `test.mjs` が同じことを1体単位で行っている**（30,000体 pass）

- [ ] **停止性**: どのシードでも有限時間で終わる。
      判定: **構造上の根拠**（引き直し上限8回＋必ず通る固定フォールバック）をコードで確認し、
      10,000 シードで無限ループ・例外0件。**引き直しが8回を超えた場合に
      フォールバック技が採用されていること**を記録して確認

- [ ] **公平性の実行責任**: `audit` が不合格にした技が、**1つも出力に残っていない。**
      判定: 出力された全技を `audit` へ再投入し、**全件合格**であること。
      これは A・B の判定そのものではなく、**「捨てる」が実行されたか**の検査である

- [ ] **形状と外見の網羅**: 10,000 シードで**全6形状**と**全4防御状態**が出現し、
      外見（色 × 武器）が **20種類以上**出る。
      判定: `test.mjs` の既存検査（現状 6 / 4 / 21 で pass）

- [ ] **後処理後の再検査**: セットの後処理で技を書き換えたあと、
      **必ず `audit` へ出し直している。**
      判定: 後処理を通った全技が出力後の再投入で合格（上と同じ検査でカバーされる）

- [ ] **容量**: **1,700 inlined bytes 以内**

## 5. 変えてはいけない前提

1. 根の不変条件12件。とくに **9**（同じシードは同じ敵を再現する）
2. `duel` の不変条件4件。とくに**決定論の規約**
3. `gen` の不変条件3件。とくに
   - **乱数系列を持つのは `roster` だけ**
   - **フォールバック技は検査を必ず通る固定値。生成しない**
4. **検査を通らない技は必ず捨てる。**「ほぼ安全」で通さない（`duel` の不変条件11）
5. **`audit` の判定を上書きしない。**`roster` は捨てるか採るかを決めるだけで、
   **合否そのものを変えられない**
6. **ラン全体を1つのシードから決める**（`gen` の親に残すもの）。1体ずつにしない

## 6. 決めないこと・任せること

**実装が決めてよい**

- 引き直し上限の値（8 は根の 1.3 の値。据え置きを推奨）
- 乱数の導出方法（実装は `seed ^ imul(tier+1, 0x9e3779b9)`）
- 役割枠の並び（実装は `[突き, 横薙ぎ, 接近/遠距離, 範囲制圧, 固有技]`）
- 山札の並べ方の材料をどう渡すか（実装は周回ごとにシャッフルするので、材料はシードだけ）
- 第2形態変異の中身（実装は固有技の威力・予備動作・硬直を +1）
- HP・体勢の値（実装は `[120,160,210]` / `[24,32,42]`）

**今回は決めない**

- ボスの体数を3から変えること（7-1 の仮置き。変えるなら `boundary_request`）
- 1体ずつ生成へ戻すこと（`fight → gen` の輪が復活する）

## 7. 分からないこと・仮置きしていること

1. **ボス何体で1ランか。**根の 1.8 は仮置きのまま、根の 6 から `duel` へ委任された。
   **仮置き: 3体**（実装が既に3体で動いている）。`provisional: true`。
   変えるなら `roster` では決められないので `boundary_request` で `gen` へ上げる

2. **後処理で不合格へ落ちたときの扱いが未定。**
   実装は後処理のあとに `validateBoss` を通すだけだが、
   **A（安全席）と B（回答2つ）が入ると、後処理が技を悪化させうる。**
   仮置き: 後処理も引き直しの対象に含め、**8回の上限を共有する**。
   超えたらその技をフォールバックへ置き換える

3. **ラン全体を持つと容量を食う。**3体 × 5技 × 安全席テーブルを同時に持つ。
   1,700 bytes は**組み立てのコードだけ**の見積もりで、**データの大きさは別**である。
   `d1` の実サイズを見積もっていない

4. **生成の待ち時間が1回に集中する。**ラン全体を作るので、
   最悪ケースは「3体 × 5技 × 引き直し8回 × 検査」になる。
   仮置き: タイトル画面で隠す。**実測していない**

5. **`audit` に A・B が入ると、引き直し率が上がる可能性がある。**
   実装の `validateBoss`（C だけ）は 30,000体で1件も落ちていないが、
   A・B は一度も動いていない。**落ちる率が高いと停止性に効く**
