## 1. これは何を決めるものか

<!-- 深さ2: 親の決定の詳細化と、それに伴う機能 -->

**戦闘が始まる前に確定するものを、どう作り、どう確かめ、どう渡すか**を決める。

親（`duel`）は「保証を予算から検査へ移す」と決めた。`gen` はそれを**機能へ分解する。**

### 機能の一覧（これが深さ3の子になる）

| 機能 | 中身 | 純粋か |
| --- | --- | --- |
| **技を1つ作る** | 形状の選択・数値の抽選・危険度の計算・禁止組み合わせの強制・帯域への補正 | 純関数（**乱数の値列**を受け取る。関数を受け取らない） |
| **公平性を検査する** | 危険包絡の計算・安全席の判定・回答2つの判定・セット単位の条件 | **純関数**（副作用なし） |
| **手順を回して組み立てる** | 乱数系列・役割枠・引き直し・フォールバック・後処理・外見・ラン全体の配分 | **唯一の状態の持ち主** |

**この3つに分ける理由は、引き直しのループを子の間に通さないためである。**

```
        ┌──────────── roster（手順と状態） ────────────┐
        │                                              │
    g1  ▼ 生成要求                        g3 ▼ 検査対象
      move ──────► g2 技1つ ──► roster ──► audit ──► g4 合否
```

**`move` と `audit` は互いを知らない。**引き直しのループは `roster` の内部に閉じる。

> 🧭 **AI**: 親の `duel-split-1` が5子案を却下した理由は
> 「**検査器と生成器の間に引き直しのループが通る**」だった。
> `move` → `audit` の直接接続を作ると、まさにそれが起きる。
> **`roster` をハブにすると、兄弟同士の線が1本も無くなる。**（2026-09-04）

### 実装済みのものとの関係

`prismatic-duel/` に**既に対応物がある**（[`design/AS_BUILT.md`](../../../AS_BUILT.md)）。

| このノードの機能 | 実装の対応 | 状態 |
| --- | --- | --- |
| 技を1つ作る | `makeMove()` / `threat()` / `harden()` / `balance()` | **動いている** |
| 公平性を検査する | `validateBoss()` | **動いているが、検査の中身が違う**（安全席が無い） |
| 手順を回して組み立てる | `generateBoss()` | **動いているが、1体ずつ**（ラン一括ではない） |

**`gen` の実装は、ゼロからではなく差分から始まる。**

## 2. なぜ要るのか

**祈りでは足りない**（親の本文2）。抜け道の無い技が1つでも生成されると、
受け入れ条件「初見」（なぜ負けたかを自分の言葉で言える）が壊れる。
しかも生成物なので**制作者がテストで踏むとは限らない。**

**ここを分けないと、検査と生成が同じ関数に混ざる。**混ざると
「検査を通らない技を、検査を緩めて通す」という直し方ができてしまい、
親の不変条件11（検査を通らない技は必ず捨てる）が守れない。
**`audit` を純関数として独立させることが、その不変条件の実効化である。**

## 3. 誰が使い、誰が影響を受けるか

- **`fight`**: `d1.run-definition` を受け取る唯一の相手。`gen` の出力形式が変わると全部ずれる
- **`read`**（親経由）: 技の形状パラメータと特性ベクトルの出所は `gen` の正本
- **将来の実装者**: 検査を通らない技を捨てる設計は、**生成が確率的に遅くなる**。
  上限とフォールバックが無いとフリーズする
- **審査員**: 1体目で理不尽を踏んだら閉じる

## 4. 終わったとどうやって分かるか（受け入れ条件）

親から4条件を主担当として割り当てられた。**`gen` で検査可能な形にする。**

- [ ] **決定論**: 同一シードから2回生成した**ラン全体**が、シリアライズしてバイト一致する。
      判定: 1,000 シードで2回ずつ `generateRun()` を呼び、JSON を比較して全一致。
      **実装済みの `test.mjs` が同じことを1体単位で既に行っている**（30,000体 pass）

- [ ] **公平性 A（安全席）**: 生成された**黄の技すべて**が安全席の検査を通っている。
      判定: 10,000 シードで全ランを生成し、黄の技すべてについて違反0件

- [ ] **公平性 B（回答が2つ）**: 生成された**すべての技**が、
      親の能力契約に対して有効な回答を2つ以上持ち、うち1つは反射神経を要求しない。
      判定: 同じ 10,000 シードで違反0件

- [ ] **停止性**: 構造上の根拠（引き直し上限8回＋必ず通る固定フォールバック）をコードで確認し、
      10,000 シードで無限ループ・例外0件。
      **実装済みの `balance()` は24回で打ち切る形で既にこれを満たしている**

- [ ] **形状と外見の網羅**: 10,000 シードで**全形状**と**全防御能力**が出現し、
      外見（色 × 武器）が20種類以上出る。
      判定: `test.mjs` の既存検査をそのまま使う（現状 6形状 / 4防御 / 21種で pass）

- [ ] **容量**: `gen` 由来のコードが **6,800 inlined bytes 以内**。
      判定: ビルドが出す inlined 値の内訳（実測は実装段階）

## 5. 変えてはいけない前提

**根から継承**（親の本文5 経由）

1. 不変条件12件すべて。とくに **7**（戦闘中の判定を生成しない）、**9**（同じシードは同じ敵）、
   **10**（反射神経に依存しない回答を最低1つ持つ）
2. **知覚の下限** 18F / 同時2件は根の仮の前提。**疑わずに使う**

**`duel` から継承**

3. **公平性の保証は検査が持つ。**予算と禁止列挙は最適化にすぎない
4. **生成は決定論的。**引き直しを含めてシードから再現できる
5. **検査を通らない技は必ず捨てる。**「ほぼ安全」で通さない
6. **プレイヤー能力契約**（親の本文5 の 12）。値まで決まっている。`provisional`
7. **形状の展開規則は `duel` が持つ。**`gen` は形状**パラメータ**の正本を持つが、
   種別 → 矩形/円への展開規則は書き換えられない
8. **ラン全体を1つのシードから決める**（`fight` へ渡すのはラン単位）

**`gen` 自身の不変条件**（このノードで著述）

9. **`audit` は副作用を持たない。**検査は判定を返すだけで、技を書き換えない。
   書き換えてよいのは `roster` だけ
10. **乱数系列を持つのは `roster` だけ。**`move` と `audit` は乱数関数を受け取るか、
    まったく使わない。2箇所から乱数を引くと決定論が壊れる
11. **フォールバック技は検査を必ず通る固定値。**生成しない

## 6. 決めないこと・任せること

**深さ3または実装が決めてよい**

- 危険度のコスト表の**具体的な数値**（実装は `DMG_COST=[0,1,3,6,9]` 等を持つ。据え置くかは深さ3）
- 帯域の値（実装は `[3+tier, 6+tier]` / 固有技 `[6+tier, 8+tier*2]`）
- ~~ボスの合計上限の値~~ → **`duel` が凍結した**（`24 + tier × 6`。本文5 の 12 の🔒）。
  `roster` は**その値を守る**だけで、決め直さない
- 形状テンプレートを**何種類持つか**（実装は6種）
- 危険包絡の**計算方法**（区間演算か離散サンプリングか）
- 安全席テーブルの**持ち方**（配列か区間の圧縮表現か）
- ボスの HP・体勢の値（実装は `[120,160,210]` / `[24,32,42]`）
- 山札の**並べ方**（実装は周回ごとのシャッフル）

**今回は決めない**

- 敵の種類を増やす仕組み、ボス以外の敵、複数体同時

## 7. 分からないこと・仮置きしていること

1. **ボス何体で1ランか。**根の 1.8 は仮置きのまま。
   **実装は3体**（`tier` 0/1/2）。仮置きとして**3体を採る**。`provisional: true`

2. **危険包絡の計算コストが分からない。**離散サンプリングだと
   10,000 シードの検証が実行時間の問題になりうる。
   仮置き: 生成はタイトル画面またはボス出現前に行い、体感を隠す

3. **安全席テーブルをラン全体ぶん持つと容量を食う。**
   実行時に再計算するほうが小さいが、**正本が2箇所になる**（不変条件8 と同じ型の危険）。
   6,800 bytes に収まるかは実装しないと分からない

| 形状と外見の網羅 | **`roster`**（外見の決定）＋ `move`（形状の抽選） |
| 容量 | 各子が自分の取り分 |

未割り当ては無い。**2子にまたがるものは、判定側が主で、`roster` が「捨てる」実行責任を持つ。**
不成立の原因が相手側にあると判断したら `boundary_request` で `gen` へ返す。

### 他の切り方との比較

- **2子案**（`move` ＋ `roster`。検査を `roster` へ畳む）: 却下。
  検査と「検査を緩める権限」が同じノードに入り、
  親の不変条件11（検査を通らない技は必ず捨てる）を守る主体が消える
- **`move` → `audit` を直結する案**: 却下。**引き直しのループが兄弟間に通る。**
  親が5子案を却下した理由そのもの
- **形状ごとに切る案**（SWEEP / THRUST / …）: 却下。6子で予算超過。
  かつ形状は `move` の内部の分岐であって、独立した実装単位ではない
- **危険度と検査を1つにする案**: 却下。危険度は**最適化**、検査は**保証**で、
  親が明示的に層を分けている（本文1の5層）。混ぜると降格した層が復活する
- 子は3つ、深さ3。予算内

### この提案自体への疑い

1. **`audit` が一番大きい**（2,600 / 6,800）。危険包絡の計算がここに全部入る。
   深さ3は分割できないので、**大きすぎたら `gen` へ差し戻す**（`README.md`「深さ3が
   1つの実装単位として大きすぎたら、その場で分割せず深さ2へ差し戻す」）
2. **`roster` の seam が4本のうち3本に触れている。**ハブなので当然だが、
   `roster` が変わると3子すべてに波及する
3. **実装済みの `validateBoss()` は `audit` に相当するが、検査の中身が違う**
   （安全席が無く、セット単位の条件で保証している）。
   **`audit` は実装済みコードの置き換えであって、拡張ではない**
