## 親からの振り分け

- **責任**: 両者を突き合わせ、1戦の決着とランの進行を決める
- **詳細化の対象**: 親の本文1の機能「突き合わせる」。根の 1.1（1戦の中身）、
  1.8（1体ごとに回復・敵側の予算だけで難易度・負けたら同じ敵へ即再挑戦）
- **継承する制約**: 根12件＋`duel` 4件＋`fight` 3件。とくに
  **8**（予告と当たり判定は同一定義。**形状の展開を行う唯一の場所**）、
  **9**（リトライでも次ボスでも生成をやり直さない）。
  接触の解決順序（`fight` の親に残すもの4）を**実行する主体**。
  `s1.presentation-state` の組み立て責任（同 5）。容量の目安 **3,600 inlined bytes**
- **割り当てられた受け入れ条件**: 宣言との一致（主）、学習が起きる（根の判定・補助とも主）、
  決定論（主）、利用可能性（前提: 安全席テーブルとプレイヤー位置を `foe` へ渡す）
- **uses_seams**: `f1.avatar-state`, `f2.foe-state`, `d1.run-definition`
- **提供する seam**: `f3.avatar-verdict` / `f4.foe-verdict`（兄弟へ）、
  **`s1.presentation-state`**（`fight` の代表として `duel` の `seam_inbox` 経由で `read` へ）
- **parent_decision_ref**: `fight@2026-09-05-decision-4` ＋ `fight@2026-09-05-split-4`

## 1. これは何を決めるものか

**`avatar` と `foe` が出会う規則、1戦の決着、ランの進行、そして `read` へ渡すもの。**

**`arena` は「敵側」でも「プレイヤー側」でもない。**
根と `duel` が「敵側／プレイヤー側で切る案」を2回却下した理由が
「**形状 × 回答手段の宣言が両者を縛る**」だったので、
**その縛るものを持つノードとして置いた。**

### 1.1 形状の展開（不変条件8 の実効化点）

**`d1` の技パラメータと、`duel` の展開規則から、現在段の矩形を1つ作る。**

| 形状 | 展開結果（`duel` の規則） |
| --- | --- |
| SWEEP | 床上 24px の横長矩形（`射程` × 24）。**ジャンプで抜けられる** |
| THRUST | ボス胸元から正面へ伸びる細い矩形（`射程` × 18） |
| SLAM | ボスを中心とする地上の広い矩形（`射程+44` × 57） |
| CHARGE | 移動中のボス本体矩形（37 × 68） |
| SHOT | 矩形なし。弾として処理する |
| RAIN | 予備動作開始時に固定した X への縦矩形（`28+射程×9` × 289） |

**`read` はこの同じ展開結果を `s1` で受け取って描く。**
**表示用の形を別に持たない**（根の不変条件8）。

> 🧭 **展開を `arena` 1箇所に閉じるのが `fight` の分割の要点である。**
> `avatar` にも `foe` にも矩形を作らせない。
> 2箇所で展開したら、**「見た目より判定が広い」事故**がいつか起きる。（2026-09-04）

### 1.2 接触の解決順序（`fight` の親に残すもの4 を実行する）

> 1. **ロール無敵**が有効なら、何も起きない
> 2. **被弾後無敵**が有効なら、何も起きない
> 3. **パリィ受付中**かつ**その技がパリィ可能（`m[F] & PARRY`）**なら、**パリィ成立**
> 4. それ以外は**被弾**

**同じ攻撃段から二重に受けない。**ヒットIDは `攻撃通し番号:段番号`。
持続が 5〜12F あっても**1段につき1回だけ。**

**パリィ成立時**（`f4` で `foe` へ通知）:

- ボスの体勢を **8 削る**
- プレイヤーのパリィ硬直を**解除する**（`f3` で `avatar` へ）
- 体勢0 なら **stagger**、残っていれば **42F の recover**

**弾は反射できる。**パリィが合うと所有者が反転し、速度・色・ダメージ・体勢値が変わる。

### 1.3 ダメージの解決

**ボスが受ける側**

| 状況 | 補正 |
| --- | --- |
| `guard` 中（SHIELD） | HP **30%** / 体勢 **35%** |
| BARRIER 有効 かつ 弾 | ダメージ **30%** |
| ARMOR かつ 通常時 | 体勢ダメージ **半減** |
| **`recover` / `stagger` 中** | HP ダメージ **1.25倍**（明確な反撃窓） |

**判定の順序**: HP0 を最優先 → 最終形態への移行 → 体勢崩し。

**プレイヤーが受ける側**: ダメージ・42F の無敵・ノックバックを `f3` で `avatar` へ。

### 1.4 ラン進行（根の 1.8）

```
title ──► fight ──► bosswin ──► fight（次のボス）──► … ──► result
            │
            └────► dead ──► fight（同じボスへ即再挑戦）
```

- **1体倒すごとにプレイヤーは全回復**
- **難易度は敵側だけで上がる**（`d1` に `tier` ごとの予算が既に入っている）
- **負けたら同じ敵へ即再挑戦。技・数値・外見は変わらない**
- **`d1` を保持し、`gen` を呼び直さない**（不変条件9・受け入れ条件「決定論」）

### 1.4.1 撃破時の奪取選択（根の 1.10）

**ボスを倒した瞬間、`arena` が選択の候補を組み立てる。**

1. `d1` から**倒したボスの全技**を取り出す（4〜5個。**予備枠のフォールバックは含めない**）
2. **今の所持技**を候補へ加える（「持ち替えない」を選べるようにする）
3. `duel` の変換規則（本文5 の 13）を適用して**プレイヤー版のパラメータ**にする
4. `s1` の「奪取の候補」と**「今どれを指しているか」（カーソル位置）**を載せる
5. **左右入力でカーソルを動かし、決定入力で確定するのは `arena` である**
6. 確定したら `f3.avatar-verdict` で `avatar` へ渡す

> 🔒 **凍結（`arena@2026-09-05-decision-5`）。`read` は選ばない。描くだけ。**
>
> **選択を `read.frame.screens` にさせると、結果を `duel` へ返す経路が要る。**
> `s1` は `duel → read` の片方向で、逆向きは**根が `split-1`〜`6` で
> 何度も苦労して消したもの**である。1つ足すと、そこから増える。
>
> **入力はもともと `duel` 側が読んでいる**（`avatar` がキーを解釈する）。
> カーソルも `arena` が持ち、**位置を `s1` に載せて `read` が描く。**
> これで `read` の不変条件8「`read` は計算しない。`s1` の値をそのまま使う」とも揃う。

**選択が済むまで次のボスへ進まない。**ラン進行（1.4）の `bosswin` がこの状態を持つ。

> 🧭 **候補にフォールバックを含めない**のは、あれが**生成物ではなく停止性のための固定技**
> だからである（`gen.roster` 1.2.1）。**プレイヤーが選ぶ対象ではない。**（2026-09-05）

### 1.5 `s1.presentation-state` の組み立て

**`read` が画面に出すために必要な `duel` 側の状態すべて。**
`fight` の代表として `arena` が組み立て、`duel` の `seam_inbox` へ出す。

| 区分 | フィールド |
| --- | --- |
| **技表示** | 形状ID / **展開済みの危険範囲**（X, Y, 幅, 高さ。円なら中心と半径）/ 発生までの残りフレーム / 予備動作の全長 / 特性ベクトル / **有効な回答手段の集合** / 多段の何段目か / 床付近か高さありか / **SHOT の狙い先**（X, Y）/ **RAIN の落下 X** |
| **技の識別** | 現在技の形状名 / 威力 / 射程 / **主色** / 副色 |
| **プレイヤー** | **中心座標**（X, Y）/ 当たり判定矩形 / 向き / 接地・滞空 / 現在の行動 / **無敵中か** / **パリィ受付中か** / HP / **最大 HP** / スタミナ / **最大スタミナ** |
| **ボス** | **中心座標**（X, Y）/ 当たり判定矩形 / 向き / **状態**（`wait`/`wind`/`active`/`recover`/`guard`/`stagger`/`shift`）/ HP / **最大 HP** / 体勢 / **最大体勢** / **異名** / **防御能力の種別** / **第2形態へ移行済みか** |
| **外見** | 体格 / 武器の形状ID / **武器シルエットの太さ**（固有技の威力）/ 長さ（同射程）/ 主色 / 副色 / 緑の輪郭の有無 |
| **弾** | 配列。各要素が 座標（X, Y）/ 速度 / **所有者** / 色 / パリィ可能か |
| **効果** | 配列。各要素が 座標 / 種別（火花・被弾・撃破）/ 残り寿命 / 色 |
| **ライフサイクル** | 開始・被弾・パリィ成功・体勢崩し・撃破・敗北・リトライ・**第2形態移行**の遷移イベント |
| **ラン** | ボス番号（0〜2）/ 総体数 / **タイム**（フレーム）/ **被弾数** / **パリィ数** |
| **結果表示** | シード（32bit）/ 技構成（全技の9パラメータ） |
| **所持技** | 形状ID / 射程 / 予備動作 / 硬直 / 多段 / 特性ベクトル / スタミナ消費 / 主張色 |
| **奪取の候補** | 撃破直後だけ。倒したボスの全技 ＋ 今の所持技（変換規則の適用後） |
| **奪取のカーソル** | 今どれを指しているか（添字）。**`arena` が持ち、`read` は描くだけ** |
| **操作割当** | 回答手段4つ ＋ 攻撃と実キーの対応 |

**出所**: `f1.avatar-state`（プレイヤー）/ `f2.foe-state`（ボス・技表示）/
`d1.run-definition`（技の識別・外見・有効回答集合・結果表示）/ `arena` 自身（弾・効果・ラン・ライフサイクル）。
**`arena` はこの4つ以外から値を作らない。**

> 🔒 **凍結（`arena@2026-09-05-decision-5`）。**
> 2026-09-04 Codex 監査 **P0-6**: 「根の `s1` は完全スナップショットを要求するが、
> **`arena` の組み立て表は旧版のままで、座標・最大値・弾・効果・ラン統計・
> 第2形態イベントなどを欠く。」**根の `split-8` の表と**同じフィールド集合**へそろえた。

**技と形状の定義部分は `d1` の値をそのまま載せ、形を作り直さない。**

### 1.6 60Hz 固定更新

可変間隔の描画を **60Hz 固定の更新**へ変換する。
**1描画あたり最大5更新に丸める** — タブ復帰時に数秒ぶんを一気に計算して、
**プレイヤーが操作できないまま攻撃を受けることを防ぐ。**

**出所は実装**（`loop()` / `step()`）。[`design/AS_BUILT.md`](../../../../AS_BUILT.md) §3・§7。

## 2. なぜ要るのか

**根の不変条件8 を守る主体が要る。**
「予告した危険範囲と、実際の当たり判定は、同一の定義から作る」は、
**展開を行う場所が1つでないと成立しない。**

**`avatar` と `foe` を互いに見えなくするためにも要る。**
両者が直接ぶつかると、無敵の判定・パリィの成立・ダメージの補正が
**どちらの持ち物か決まらない。**`arena` が全部を持つと、優先順が1箇所に書ける。

## 3. 誰が使い、誰が影響を受けるか

- **プレイヤー**。理不尽かどうかは接触の解決順序で決まる
- **`avatar` / `foe`**: `arena` からの `f3` / `f4` でしか外界を知らない
- **`read`**（`duel` 経由）: `s1` の組み立て主体は `arena` である。
  **`arena` が展開結果を渡すから、`read` は形を持たなくて済む**
- **`gen`**: `d1` を渡すだけ。**`arena` は `gen` へ何も返さない**

## 4. 終わったとどうやって分かるか（受け入れ条件）

- [ ] **宣言との一致（主担当）**:
      **`d1` が宣言した回答手段すべてで、その技を無傷で抜けられる。**
      判定: 10,000 シードの全技について、宣言された各手段の台本入力を走らせ、
      **被弾0**であること。違反0件

      > 🧭 **これが根の共通語彙「宣言と実装が食い違ってはならない」の検査である。**
      > `gen` の `audit` が「回答が2つある」と判定しても、
      > **`arena` の判定が違えば嘘になる。**両側から挟む。（2026-09-04）

- [ ] **予告と判定が一致する**（不変条件8）:
      **`s1` に載せた危険範囲と、実際に当たった矩形がビット単位で同一。**
      判定: 全フレームで両者を記録して比較。**別々に計算していないことをコードでも確認**

- [ ] **二重ヒットが無い**:
      **1つの攻撃段から2回ダメージを受けない。**
      判定: 持続が最大（12F）の技で、1段につきダメージイベントが1回だけ

- [ ] **決定論（リトライ）**:
      **`d1` を受け取ってから捨てるまで、生成関数の呼び出しが0回。**
      判定: コードで確認 ＋ 敗北 → 再挑戦で技構成がバイト一致

- [ ] **学習が起きる（根の判定）**:
      同一シードへの連続挑戦で、1回目と3回目の被弾数が減っている。
      判定: 根の 4「学習」のまま。実施者は制作者でよい

- [ ] **学習が起きる（補助・台本比較）**:
      (a) 完全ランダム入力と (b) 山札を知っている台本入力を各20回。
      **(b) の平均被弾が (a) の 50% 以下**

- [ ] **タブ復帰で理不尽に死なない**:
      **1描画あたりの更新が5回を超えない。**
      判定: 5秒間タブを隠して復帰し、被弾が0であること

- [ ] **容量**: **3,600 inlined bytes 以内**

1. 根の不変条件12件。とくに

   - **9** 同じシードは同じ敵。リトライでも次ボスでも生成をやり直さない
   - **10** すべての生成攻撃は反射神経に依存しない回答を最低1つ持つ
2. **形状の展開を実戦で行うのは `arena` だけ**（`fight` の不変条件8）。

   **ただし展開規則そのものは `duel` が持ち**（`duel` の親に残すもの4）、
   **`gen.audit` が生成時の検査で同じ規則を使う。**
   「`arena` だけ」は**実戦での実行者**の話であって、規則の所有者の話ではない

   > 🔒 **凍結（`arena@2026-09-05-decision-5`）。**旧文は「展開するのは `arena` だけ」と

5. **`s1` に載せる技と形状の定義は `d1` の値そのまま。**作り直さない
6. **`d1` を書き換えない。**受け取った定義は読み取り専用。**例外は無い。**

   > 🔒 **凍結（`arena@2026-09-05-decision-5`）。**旧文は「例外は第2形態変異だけ」としていたが、
   > **第2形態は `gen` が生成時に確定・検査し、`d1` が両形態を運ぶ**形へ変わった

## 6. 決めないこと・任せること

**実装が決めてよい**

- ダメージ補正の値（SHIELD 30/35% / BARRIER 30% / ARMOR 半減 / 反撃窓 1.25倍）
- BARRIER の破壊時間（実装は 180F）
- 弾を反射したときの値（実装は 速度 ×1.35 反転 / ダメージ3 / 体勢7）
- パリィで削る体勢量（実装は 8）
- 画面揺れ・停止フレーム（`freeze` / `shake`）の演出値
- 1描画あたりの最大更新回数（実装は 5）
- 画面遷移の入力割り当て

**今回は決めない**

- 接触の解決順序（`fight` の親に残すもの4）
- 展開を2箇所に分けること

## 7. 分からないこと・仮置きしていること

1. **「宣言との一致」の台本入力をどう書くか分からない。**
   「ジャンプで越える」を機械的に実行する入力列は、技ごとにタイミングが違う。
   **仮置き**: 危険包絡の時系列から**越えるべき時刻を逆算**して入力を組む。
   `provisional: true`。**`audit` が包絡を計算しているので、その結果を検査でも使えるはず**だが、
   `arena` は `audit` を知らない（兄弟ですらない）。**テスト側で共有する形になる**

2. **`s1` の頻度と粒度が未定。**毎フレーム全部渡すのか、差分だけかを決めていない。
   容量にも効く。仮置き: 毎フレーム全部（同じメモリを読むだけなので実質コスト0）

3. **交代を削ったあとの敗北条件。**実装は全滅で `dead` だが、1人なら HP0 で即 `dead`。
   **難易度が上がる**（`avatar` の 7-3 と同じ問題）。
   `arena` では調整できない — 根の 1.8 が「難易度は敵側の予算だけで上げる」と定めている

4. **3,600 bytes に収まるか未検証。**展開 ＋ 接触解決 ＋ ダメージ ＋ ラン進行 ＋
   `s1` 組み立て ＋ 60Hz ループが全部ここに入る。**`fight` の3子で最も詰まっている**

5. **「学習が起きる」を `arena` が測るのは、本当は測定であって実装ではない。**
   受け入れ条件の判定手段としてここに置いたが、
   **製品コードに測定を残すと容量を食う。**
   仮置き: 測定はビルド時に外す（`audit` の `validateBoss` が Terser で落ちるのと同じ手）
