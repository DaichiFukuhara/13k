## 1. これは何を決めるものか

<!-- 深さ2: 親の決定の詳細化と、それに伴う機能 -->

**確定したランを受け取ってから、勝つか負けるかが決まるまで**を決める。

### 機能の一覧（これが深さ3の子になる）

| 機能 | 中身 |
| --- | --- |
| **プレイヤーを動かす** | 入力・バッファ・行動の状態機械・移動/ジャンプ/ロール/パリィ・スタミナ |
| **ボスを動かす** | 行動の状態機械・山札・**選択時の条件**・防御能力・体勢・第2形態変異 |
| **突き合わせる** | 形状の展開・接触の解決・ダメージ・ラン進行・`s1` の組み立て |

### 構造: 突き合わせる場をハブにする

```
   avatar ──f1.avatar-state──►  arena  ◄──f2.foe-state── foe
      ◄──f3.avatar-verdict───         ───f4.foe-verdict──►
```

**`avatar` と `foe` の間に線は無い。**両者は互いを知らず、`arena` だけが両方を見る。

**これは不変条件8（予告と当たり判定は同一定義）の実効化でもある** —
形状の展開を行う場所を `arena` 1箇所に閉じると、判定が2箇所に分かれない。

> 🧭 **AI**: プレイヤー側／敵側で切る案は、根と `duel` で2回却下されている
> （「形状 × 回答手段の宣言」が両者を縛るため）。
> **ここで採れるのは、両者を縛るものを第三のノードへ出す形だけである。**
> `arena` は「敵側」でも「プレイヤー側」でもなく、**両者が出会う規則**を持つ。（2026-09-04）

### 実装済みのものとの関係

## 2. なぜ要るのか

根の 1.4 は「すべての生成攻撃は最低2種類の有効な対処を持つ」と要求し、
`gen` はそれを**生成時に検査する。**しかし**検査が正しくても、
戦闘側の実装が宣言どおりに動かなければ嘘になる。**
根の共通語彙が「**宣言と実装が食い違ってはならない**」と書いているのはこのことである。

**`fight` は、`gen` の宣言を現実にする側である。**
「ジャンプで越えられる」と宣言された技が実際に越えられるかは、
`avatar` のジャンプと `arena` の判定が決める。

## 3. 誰が使い、誰が影響を受けるか

- **プレイヤー**（審査員・投票者）。1戦の手触りはすべてここで決まる
- **`read`**（親経由）: `s1.presentation-state` を組み立てるのは `fight` である。
  戦闘状態とライフサイクルを持つのが `fight` のため
- **`gen`**: 一方的に受け取るだけ。**`fight` は `gen` へ何も返さない**
- **将来の実装者**: `fight` は `duel` の 10,900 / 18,500 bytes（59%）を占める。
  容量が足りなくなったとき最初に削られる

## 4. 終わったとどうやって分かるか（受け入れ条件）

- [ ] **利用可能性**（選択時条件の実効化・主担当）:
      **黄の技が選ばれた瞬間、プレイヤーは必ずその技の安全席の中に居る。**
      判定: ランダム入力の自動プレイを 1,000 戦走らせ、
      黄の技が発動した全フレームで、発動時のプレイヤー中心が安全席内にあったこと。違反0件

- [ ] **宣言との一致**（根の共通語彙「宣言と実装が食い違ってはならない」）:
      **`d1` が「ジャンプで越えられる」と宣言した技は、実際にジャンプで越えられる。**
      判定: 各技について台本入力（宣言された回答手段だけを使う）を走らせ、
      **宣言された回答すべてで無傷で抜けられること。**10,000 シードの各技で違反0件

- [ ] **学習が起きる（根の判定）**:
      同一シードへの連続挑戦で、1回目と3回目の被弾数が減っている。

- [ ] **学習が起きる（補助・台本比較）**:
      同一シードのボスに対し、(a) 完全ランダム入力と (b) 山札を知っている台本入力を各20回。

- [ ] **決定論（リトライ）**:
      **敗北後の再挑戦と、次ボスへの遷移で、`gen` を呼び直さない。**
      判定: `d1` を受け取ってから捨てるまで、生成関数の呼び出しが0回であること（コードで確認）

- [ ] **容量**: `fight` 由来のコードが **10,900 inlined bytes 以内**

## 5. 変えてはいけない前提

**根から継承**

1. 不変条件12件。とくに **7**（戦闘中の判定を生成しない）、**8**（予告と判定は同一定義）、
   **9**（同じシードは同じ敵）、**10**（反射神経に依存しない回答）
2. **回答手段は4つだけ**（移動 / ジャンプ / ローリング / パリィ）。増やさない
3. **資源はスタミナ1本**（1.5）。**残機・控え・交代を作らない**
4. **X = 地上の移動軸 / Y = ジャンプ中のみの回避軸 / Z = 無し**（1.7）。空中制御を持たせない

**`duel` から継承**

5. **当たり判定の形状を独自に持たない。**`d1` のパラメータを**親の展開規則**で展開するだけ
6. **プレイヤー能力契約**（親の本文5 の 12）。**±25% まで調整可。範囲外は `boundary_request`**
7. **リトライでも次ボスでも生成をやり直さない**

**`fight` 自身の不変条件**（このノードで著述）

8. **形状の展開を行うのは `arena` だけ。**`avatar` も `foe` も危険範囲の矩形を作らない。
   2箇所で展開すると不変条件8 が壊れる
9. **`avatar` と `foe` は互いを直接読まない。**必要な相手の情報は `arena` 経由で受ける
10. **能力契約の値を動かしたら、`gen` の検査結果は古くなる。**
    ±25% の範囲内でも、動かした時点で**受け入れ条件「宣言との一致」を再検査する**

    > ⚠️ **これは `duel-split-2` の未検査リスクとして記録されているものである**
    > （親の承認証跡「残るリスク」）。`fight` 側の不変条件として引き受け、
    > **範囲内の調整でも再検査を義務づける**ことで塞ぐ。
    > 再検査で不成立なら `boundary_request` で `duel` へ返す。（2026-09-04）

## 6. 決めないこと・任せること

**深さ3または実装が決めてよい**

- プレイヤー能力契約の**±25% の範囲内での調整**（範囲外は `boundary_request`）
- スタミナの最大値・消費量・回復速度と停止時間（能力契約に含まれない。公平性の検査に効かない）
- 入力バッファのフレーム数（実装は ジャンプ7F / その他5F）
- 攻撃の威力・リーチ・発生・全体フレーム
- ボスの待機距離と寄せ方（実装は 105〜245 px）
- 体勢を崩したときの隙の長さ（実装は 110F）
- 第2形態変異の中身（実装は固有技の威力・予備動作・硬直を +1）
- 1体あたりの目標時間

**今回は決めない**

- プレイヤーの成長・装備・スキル選択
- 難易度設定、アシスト機能

## 7. 分からないこと・仮置きしていること

1. **交代を削ったあとのスタミナ設計。**実装は3人分のスタミナがあり、
   **控えのほうが回復が速い**（0.5/F 対 0.3/F）ことで交代に資源上の意味を持たせていた。
   1人になるとその層が消える。
   仮置き: 根の 1.5 の「消費後しばらく回復が止まる」（実装は 30F）だけで層を作る。
   `provisional: true`。**深さ3の `avatar` で決める**

2. **交代を削るとプレイヤーが弱くなる。**実装は実質3残機で、
   1人が落ちても続けられた。1人にすると難易度が上がる。
   仮置き: HP を上げるのではなく**ボス側の危険度予算で調整する**（根の 1.8 の方針に従う）。
   `gen` の担当になるので、成立しなければ `boundary_request` で `duel` へ返す

3. **「宣言との一致」の台本入力をどう書くか分からない。**
   「ジャンプで越える」を機械的に実行する入力列は、技ごとにタイミングが違う。
   仮置き: 危険包絡の時系列から**越えるべき時刻を逆算**して入力を組む

4. **選択時条件（黄）を実装するには、安全席テーブルを毎フレーム参照する。**
   実装の `nextMove()` は距離だけを見ており、テーブル参照は無い。
   容量と速度のコストが未見積もり

### 他の切り方との比較

- **敵側 / プレイヤー側の2子案**: 却下。根と `duel` で2回却下されている切り方と同じ。
  「形状 × 回答手段の宣言」が両者を縛るので、**縛るものの持ち主が居なくなる**
- **4子案**（`avatar` / `foe` / `clash` / `run`）: 却下。`clash` と `run` の間に
  「撃破・敗北 → 次へ進む」の線が通り、seam が6端点へ増える。
  ラン進行は接触の結果を受けるだけなので、`arena` に畳んで線を消した
- **状態機械ごとに切る案**（`wind` / `active` / `recover` を別ノードに）: 却下。
  ハーネスの役割を子にするのと同じ型の誤り（工程や内部フェーズは課題の分割ではない）
- **`arena` を置かず `avatar` ⇄ `foe` を直結する案**: 却下。
  **形状の展開が2箇所になり、不変条件8 が壊れる**
- 子は3つ、深さ3。予算内

### この提案自体への疑い

1. **3子とも 3,400〜3,600 bytes でほぼ均等。**これは「均等に割れた」のではなく
   **見積もりの根拠が薄い**兆候かもしれない。実装の実測（`AS_BUILT.md`）から
   逆算していない
2. **`arena` が受け取る seam が3本**（`f1` / `f2` / `d1`）。ハブなので当然だが、
   3子の中で最も壊れやすい
3. **交代を削る作業量を見積もっていない。**実装の `p` は
   `hp` / `st` / `delay` / `down` がすべて3要素配列で、
   `aliveNext()` / `swap` / `drawParty()` が絡む。**削るのも作業である**
4. **`foe` の「選択時の条件」は実装に無い。**実装の `nextMove()` は距離だけを見る。
   安全席テーブルの参照は**新規に書く部分**であり、ここだけ実測の裏付けが無い
