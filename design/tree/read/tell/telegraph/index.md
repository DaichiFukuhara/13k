### 1. 決めるもの

全6形状のwindに実 `WIND[m[W]-1]` と残り `b.timer` の線形進行を使う。
矩形は全体輪郭を残して底から上へ充填する。SHOTは全射線を破線で残し、発射点から実線を伸ばす。
RAINは未発生の全段を `moveRect(m,i,b)` で展開し、後段を薄い破線と段番号、現在発生を濃い実線と全面塗りで区別する。
CHARGEは実 `b.face` の短い矢印を頭上に出す。本体矩形以外の経路を危険判定として塗らない。

### 2. なぜ要るか

色だけでは発生までの残り時間が分からず、RAINの後段とCHARGEの向きを初見で見落とすため。

### 3. 利用者

初見と同じボスへ再挑戦するDesktopプレイヤー。無音でも範囲・時間・段順・方向を読む。

### 4. 受け入れ条件

- [x] G1（T2）: 全6形状・4つのwind長で開始/半分/直前の充填が実時間に一致する。
- [x] G2（T3）: RAINの未発生全段が共有矩形と一致し、発生済み段と段間の現在段を濃く表示しない。
- [x] G3（T3）: 左右CHARGEの矢印がfaceと一致し、SHOTは射線と発射までの進行がある。
- [x] G4（T5）: trialの標的に敵予告を出さず、反復描画で戦闘状態を変更しない。
- [ ] G5（T6）: 統合実画面・ZIP容量は親で確認。人間の初見理解・18F知覚は未検証として残す。

### 5. 不変条件とseam

危険範囲の全体矩形は `moveRect` の戻り値そのまま。充填・番号・方向記号は装飾であり判定を生成しない。
実更新器はactiveの判定後にtimerを増やすため、描画は `max(0,b.timer-1)` を使い、timer=0は未発生として薄く示す。
色は既存 `attackColor`、状態は読み取り専用。Canvasのsave/restoreで描画属性も復帰する。
段番号はY=128、矢印は頭上に置き、HUD・trial案内を避ける。trialでは即returnする。
親のモノリシック実装継続を適用し、旧本文のsnapshot物理分離・装飾を含む座標算術禁止は今回の要件にしない。

### 6. 実装へ任せるもの

破線の長さ、薄さ、線幅は軽量なCanvas描画で決める。形状・戦闘値・生成器・HUDは編集しない。
全体容量は根の13,312 bytes実測を正本とし、旧葉の1,400 inlined bytes目安で機能を落とさない。

### 7. 未確定

RAINの全段予告と旧同時予告上限の解釈差は根が受理し、根F2でRAINに限り最大3箇所へ更新した。段番号と破線で区別する。
実画面と人間知覚の最終判断は親へ返し、自動検査で代替しない。

## 1. これは何を決めるものか

**予備動作が始まってから攻撃判定が終わるまで、画面に何が出るか。**

### 1.1 描くもの

| 対象 | `s1` から使う値 | 描き方 |
| --- | --- | --- |
| **危険範囲** | **展開済みの矩形**（X, Y, 幅, 高さ） | 半透明で塗る ＋ 枠線 |
| **発生時刻** | 発生までの残りフレーム | **不透明度を上げていく**（充填） |
| **弾（SHOT）** | ボス位置と狙い先の Y | **射線**を引く（矩形が無いため） |
| **段** | 多段の何段目か | 現在段の矩形だけを出す |

**座標を1つも計算しない。**`s1` が運んできた矩形をそのまま塗る。

> ⚠️ **これがこのノードの全部である。**
> 実装の `drawTelegraph()` は `moveRect()` を呼ぶが、
> **`moveRect()` は判定側と共有された唯一の形状定義**である
> （[`design/AS_BUILT.md`](../../../../AS_BUILT.md) §3）。
> ツリーの設計ではその展開を `arena` が行い、**結果を `s1` に載せて渡す。**
> **`telegraph` は展開すら行わない。**

### 1.2 充填（「いつ」を色なしで示す）

**不透明度が予備動作の進行率に比例して上がる。**

| 段階 | 不透明度 |
| --- | ---: |
| 予備動作の開始 | 0.08 |
| 予備動作の終了直前 | 0.28 |
| **攻撃判定中** | **0.45** |

**色を使わない。**濃さだけで「いつ来るか」が読める（`read` の不変条件9）。

**出所は実装**（`drawTelegraph()`）。

### 1.3 「どこ」を色なしで示す

**矩形の位置と大きさだけで、どこが危険かが分かる。**

- 床付近の技（SWEEP）は**床に貼りつく薄い帯**として出る → ジャンプで越えられると分かる
- 高さのある技（SLAM）は**縦に厚い矩形**として出る → 越えられないと分かる
- 縦に落ちてくる技（RAIN）は**天井から床までの柱**として出る

**根の 1.7 の「床付近か高さありか」が、そのまま矩形の高さとして見える。**
**色を消しても、ジャンプで越えられるかが読める。**

### 1.4 色は `palette` から受ける（seam `t1` / `t2`）

**色値を直書きしない**（`tell` の不変条件8）。
`s1` の特性ベクトル**と「それが何を示すか」（予告の危険範囲か / 弾の射線か）**を
**`t1.color-request`** で `palette` へ渡し、
**`t2.color-result`** で返ってきた**色値と冗長化の指示**を使う。

> 🔒 **凍結（`telegraph@2026-09-05-decision-3`）。**旧文は「関数呼び出しであって seam ではない」
> と書いていたが、**親 `tell` の現行決定では `t1` / `t2` の seam である**
> （2026-09-04 Codex 監査 **P0-2**）。

## 2. なぜ要るのか

**根の不変条件8 の `read` 側の実効化点がここである。**

「予告した危険範囲と、実際の当たり判定は、同一の定義から作る。表示用の形を別に持たない」を
守る方法は2つある。

| 方法 | `telegraph` の扱い |
| --- | --- |
| 同じ関数を両方から呼ぶ | 実装がこれ（`moveRect()` の共有） |
| **片方が計算し、結果を渡す** | **ツリーはこれ。`arena` が展開し `s1` で渡す** |

**後者のほうが強い。**前者は「同じ関数を呼び忘れる」ことがありうるが、
後者は**`telegraph` に計算能力そのものが無い。**

## 3. 誰が使い、誰が影響を受けるか

- **審査員・投票者**。初見で最初に見るのがこれ
- **`palette`**: `t1.color-request` で色を要求し、`t2.color-result` で
  **色値と冗長化の指示**を受ける。**seam である**（`tell` の `split-2`）
- **`duel.fight.arena`**（親経由）: `s1` の危険範囲を作る側。
  **`arena` の展開が変わると `telegraph` の見た目が全部変わる**
- **`duel.gen`**（間接）: 知覚の下限（18F）が成立しないと `telegraph` が
  `boundary_request` を上げ、根が値を変え、生成が変わる

      **ジャンプすべきか否かを8回以上正しく選べる**こと

- [ ] **容量**: **1,400 inlined bytes 以内**

## 5. 変えてはいけない前提

1. 根の不変条件 **8**（予告と当たり判定は同一定義。表示用の形を別に持たない）
2. **`read` は危険範囲を計算しない**（`read` の不変条件8）。
   **「描画のために少し補正する」こともしない**
3. **色を決めるのは `palette` だけ**（`tell` の不変条件8）。色値を直書きしない
4. **色を使わない手がかりを常に2つ以上出す**（`read` の不変条件9）。
   矩形（どこが）と充填（いつ）は色に依存しない
5. **描画順序**: 背景の次、弾より前（`tell` の親に残すもの4）
6. **`s1` を書き換えない**

## 6. 決めないこと・任せること

**実装が決めてよい**

- 不透明度の具体値（実装は 0.08 → 0.28 → 0.45）
- 枠線を描くか、太さ、点線か実線か
- 弾の射線の描き方（実装は直線）
- 充填の曲線（線形か、終盤で加速するか）
- 段が変わるときの見せ方

**今回は決めない**

- 危険範囲の形を変えること（`arena` が展開したものをそのまま使う）
- 予告に文字を出すこと（実装は技名を出しているが、**`frame` の HUD の担当**）

## 7. 分からないこと・仮置きしていること

1. **知覚の下限 18F は現状どの技も踏まない。**実装の最短は 24F。
   **検証用に 18F の技を手で作って測る**必要がある。
   仮置き: 検証専用のシードまたはデバッグ入力を用意する。`provisional: true`

2. **同時2件の読み分けを、実装で作れるか未検証。**
   実装は1体しか居ないので `wind` 中に別の技が始まらない。
   **同時2件が起きるのは弾が複数残る場合だけ**（`foe` の 7-4）。
   検証のために人為的に2件出す手段が要る

3. **充填の曲線が線形でよいか分からない。**線形だと「終盤の切迫感」が薄い可能性がある。
   実測していない

4. **`s1` を毎フレーム全部読むのか、差分かは `arena` が決める**（`arena` の 7-2）。
   `telegraph` はどちらでも動くが、**差分だと前フレームの状態を持つ必要が出て、
   「計算しない」が崩れる方向に働く**
