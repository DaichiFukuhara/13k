## 1. これは何を決めるものか

**「この技を何色で出すか」と、「色を消しても同じ情報が出ているか」の2つ。**

**描画しない。**色を返す関数と、**冗長化の規則**を持つだけである。

### 1.1 7色の語彙（根の 1.6。`read` が持つ表）

| 色 | 示す傾向 | 対応する技のパラメータ |
| --- | --- | --- |
| **赤** | 高威力 | 威力 ≥3 |
| **橙** | 長い攻撃判定・残留 | 持続が最大 |
| **黄** | 短い予備動作 | 予備動作 ≤2 |
| **緑** | 防御能力 | ボスが防御能力を持つ |
| **青** | 長射程 | 射程4 |
| **藍** | 追尾 | 追尾 ≥1 |
| **紫** | 多段・特殊変化 | 段数 >1 |

**この対応は `read` が持つ表であり、`palette` は変えられない。**

### 1.2 1技が複数の特性を持つときの優先順

**1つの技が複数の特性を持つことは普通にある。**色は1つしか塗れない。

| 順 | 特性 | 色 |
| ---: | --- | --- |
| 1 | 高威力（威力4） | 赤 |
| 2 | 追尾 | 藍 |
| 3 | 短い予備動作（最速） | 黄 |
| 4 | 長射程（射程4） | 青 |
| 5 | 多段 | 紫 |
| 6 | （どれも無ければ）**ボスの主色** | — |

**出所は実装**（`attackColor()`）。[`design/AS_BUILT.md`](../../../../AS_BUILT.md) §3。

> ⚠️ **この順序の根拠が実装に書かれていない**（`tell` の 7-4）。
> **仮説としては「即死につながる順」**である — 高威力は1発が重く、
> 追尾は位置取りを無効にし、高速は反応時間を奪う。**7-1 で扱う。**

### 1.2.1 奪取技の色（根の 1.10）

**プレイヤーが持っている技にも色が付く。**ただし**出るのは4色だけ**である。

| 色 | 出るか | 理由 |
| --- | --- | --- |
| 黄 / 青 / 紫 / 橙 | **出る** | 予備動作・射程・多段・持続を引き継ぐため |
| 赤 / 藍 / 緑 | **出ない** | 威力は正規化、追尾は削除、防御は攻撃技でない |

**`s1` が運ぶ特性ベクトルは変換後の値**（`duel` の 13.2）なので、
`palette` は**ボスの技と同じ関数で色を決められる。**分岐を増やさない。

### 1.3 ボスの主色（根の 1.6 の後半）

**ボスの主色は「最も危険度へ寄与した特性」から決まる。**
これは `gen.roster` が生成時に決めて `s1` に載せてくる。
**`palette` は色値へ写すだけ。**

### 1.4 冗長化の規則（不変条件11 の本体）

**色が示す情報はすべて、色以外の手段でも示されていなければならない。**

| 色が示すもの | 色以外の手段 | 担当 |
| --- | --- | --- |
| **高威力**（赤） | **武器シルエットの太さ**（`actors`。命中前に見える）＋ 危険範囲の**縦の厚み**（`telegraph`）。**被弾後の画面揺れは数えない** | `actors` / `telegraph` |
| **長い持続**（橙） | 攻撃判定中の**表示時間の長さ**そのもの | `telegraph` |
| **短い予備動作**（黄） | 充填が**速く濃くなる**こと | `telegraph` |
| **防御能力**（緑） | ボスの**輪郭**と、構え中の板 | `actors` |
| **長射程**（青） | 危険範囲の**横幅**そのもの | `telegraph` |
| **追尾**（藍） | 予備動作中に危険範囲が**動く**こと | `telegraph` |
| **多段**（紫） | 段が**繰り返し出る**こと | `telegraph` |

> 🔒 **凍結（`palette@2026-09-04-decision-2`）。**2026-09-04 の Codex 監査（**実装しながら3**）:
> **「`read` は `s1` の危険座標を変更せず描画する契約なので、
> 「危険範囲を太くする」は書けない。命中前に見える別チャネルへ固定せよ。
> **被弾後の画面揺れだけでは予告の冗長化にならない。」**
>
> **主チャネルを武器シルエットの太さ（`actors`）にした。**戦闘開始前から見える。
> 危険範囲の縦の厚みは**形状が決めるもの**（`duel` の展開規則）で `read` は動かせないが、
> **形状ごとの厚みの違いは高威力技の傾向と相関する**ので補助として残す。

**この表が「色だけに依存させない」の実効化である。**
**すべての行に色以外の手段が埋まっていること**が、`palette` の責任である。

> 🧭 **`palette` が描画しないのに冗長化の規則を持つのは、
> 検査できる場所を1箇所にするためである。**
> 規則が `telegraph` と `actors` に散っていると、
> **「全部の色に代替があるか」を確かめる場所が無い。**（2026-09-04）

## 2. なぜ要るのか

**根の不変条件11 は「色だけに依存させない」と定めるが、
守っているかを確かめる場所が無いと、宣言に終わる。**

受け入れ条件「テーマ」は
**「色を取り除くと、敵の性格を推測する手段が予備動作の観察だけになり、
初見の判断が推測から反応へ落ちる」**を1文で説明できることを求める。

**これは色が効いていることの主張である。**
一方で不変条件11 は**色が無くても遊べること**を求める。
**両方を同時に満たす必要がある** — 色は**推測を速くする**が、**必須ではない。**

**`palette` はこの2つの境界を管理する唯一のノードである。**

## 3. 誰が使い、誰が影響を受けるか

- **色覚特性のあるプレイヤー**。冗長化の規則が直接効く
- **`telegraph` / `actors`**: 色を得るために呼ぶ。**冗長化の規則の実行者でもある**
- **審査員**: 「テーマ（Unicorns and Rainbows）が装飾ではなくルールとして働いている」の
  採点対象がここ

## 4. 終わったとどうやって分かるか（受け入れ条件）

- [ ] **色を取り除いても遊べる**（主担当）:
      色を輝度のみのグレースケールへ置換しても、
      「どこが危険か」「いつ発生するか」が読める。
      判定: グレースケール版で1体目を通しプレイし、**被弾がカラー版の 1.5倍以内**

- [ ] **冗長化の表に穴が無い**:
      **1.4 の表のすべての行に、色以外の手段が埋まっている。**
      判定: 表を読んで空欄が0件。加えて**各手段が実際に実装されている**ことを
      `telegraph` / `actors` のコードで確認

      > 🧭 **これが `palette` の一番の仕事である。**
      > グレースケール検査は「通った / 通らない」しか分からない。
      > **どの色に代替が無いか**は、表を見ないと分からない。（2026-09-04）

- [ ] **テーマ**（主担当）:
      同じグレースケール検査で、**1体目の初見プレイの被弾が有意に増える**ことを示す。
      **これが「色が効いている」ことの根拠になる。**
      判定: 初見の被験者を2群に分け、カラー版とグレースケール版の初見被弾を比べる

      > ⚠️ **上の条件（1.5倍以内）と、この条件（有意に増える）は
      > 逆方向を要求している。**「色が無くても遊べる」かつ「色が効いている」なので、
      > **被弾は増えるが 1.5倍は超えない**という帯に収める必要がある。
      > **これが虹をルールにするということの、検査可能な形である**

- [ ] **色を決めるのが `palette` だけ**:
      `telegraph` と `actors` に色値の直書きが**1件も無い。**
      判定: 色リテラル（`#` で始まる文字列など）の grep が `palette` 以外で0件

- [ ] **容量**: **600 inlined bytes 以内**

## 5. 変えてはいけない前提

1. 根の不変条件 **11**（色だけに依存させない）。**範囲・時間・動きでも同じ情報を示す**
2. **7色の語彙**（`read` が持つ表）。**色と特性の対応を変えない**
3. **色を使わない手がかりを常に2つ以上出す**（`read` の不変条件9）
4. **描画しない。**色を返す関数と規則だけを持つ
5. **ボスの主色は `gen` が決めたもの**（`s1` で来る）。`palette` は色値へ写すだけ

## 6. 決めないこと・任せること

**実装が決めてよい**

- 具体的な色値（実装は7色の16進値を持つ）
- 明度・彩度の調整（背景とのコントラストを取るため）
- グレースケール変換の式（輝度の重み）
- 色を返す関数の形（配列添字か、条件分岐か）

**今回は決めない**

- 7色と特性の対応（`read` の表）
- 冗長化の表から行を削ること

## 7. 分からないこと・仮置きしていること

1. **優先順（1.2）の根拠が実装に書かれていない。**
   仮説として「即死につながる順」を置くが、検証していない。
   **`provisional: true`。**プレイテストで「読み違えやすい組み合わせ」が出たら見直す。
   **順序は `palette` の担当なのでここで変えられる**（`read` の表は対応であって順序ではない）

2. **グレースケール検査の閾値 1.5倍に根拠が無い**（`read` の 7-3 から引き継ぎ）。
   変えるなら `boundary_request`

3. **「テーマ」の判定に被験者が2群要る。**根の 7-2（被験者を確保できるか未定）が
   ここで2倍に効く。**確保できない場合の代替が無い**

4. **冗長化の表の「高威力＝危険範囲の厚み」が本当に読めるか未検証。**
   実装は威力で矩形の厚みを変えていない（形状ごとに固定）。
   **表に書いたものの、実装がまだ無い行がある**

   | 行 | 実装の有無 |
   | --- | --- |
   | 高威力 → **武器シルエットの太さ** | **無い。新規に作る**（`actors` 7-1） |
   | 長い持続 → 表示時間 | ある |
   | 短い予備動作 → 充填の速さ | ある |
   | 防御能力 → 輪郭 | ある（BARRIER のみ） |
   | 長射程 → 横幅 | ある |
   | 追尾 → 範囲が動く | ある |
   | 多段 → 繰り返す | ある |

   **「高威力 → 厚み」は新規に作る必要がある。**または別の手段へ差し替える
