### 1. 決めるもの

「構えを読む・避ける・隙に当てる・技を奪って試す」の各段階を画面で対応付ける。
tellは全6形状の構え/発生/硬直の姿勢と時間予告、frameは目的/操作/ゲージ/成功と失敗の理由/奪取と試用の案内を詳細化する。
共有の技展開・戦闘状態を読む方針は維持し、装飾姿勢だけを読み取り値から算出する。

### 2. なぜ要るか

単純な姿勢では発生と反撃窓が見えず、色の凡例や被弾理由が不足している。
奪取は開始時に魅力が伝わらず、候補の数値だけでは使用感が分からない。
情報を増やすだけで中央の攻防を隠さないことを解決条件に含める。

### 3. 利用者

初めて短時間遊ぶDesktopプレイヤー。開始から操作と技奪取の目的を知れる。
経験者は試用を飛ばし、同じ相手への再挑戦や次戦をすぐ開始できる。

### 4. 受け入れ条件

- [ ] R1（根F1 / frame）: 開始画面で「倒した敵の技を1つ奪える」が読める。戦闘中のHP/ST/体勢、移動/ジャンプ/ロール/パリィ/攻撃の操作、色の意味が実際の割当と一致する。
- [ ] R2（根F2 / tell）: 全6形状でwind/active/recoverを姿勢から区別できる。充填は実際のwind全長と残りFに従い、短い技でも完了時点を偽らない。RAINは後段の位置も共有展開から描き、CHARGEは進行方向を示す。
- [ ] R3（根F3 / frame主、tell協力）: `feedback.kind`のhit/counter/parry/hurt/tiredを識別できる。counterは実際のrecover/staggerへの命中イベントのみ。描画側が姿勢から成功を推定しない。
- [ ] R4（根F4 / frame主、tell協力）: 被弾時と死亡画面で原因の技と短い対処例を読める。`lesson(m)`の意味を変えず、SHOTの弾パリィ対応を含め、不可の技をパリィ可能と案内しない。tiredはスタミナ不足として示す。対処は安全保証と表現しない。
- [ ] R5（根F5の提示 / frame、tellは試用描画）: 候補選択、任意の試用、候補へ戻る、次戦または最終結果へ進む操作が分かる。試用中の技/消費/標的を表示し、pause復帰後も試用であると分かる。通常戦の表示を試用中の実状態と取り違えない。
- [ ] R6（根F6/F7のread分 / 各子と統合）: 全6形状・被弾・パリィ・死亡・試用出入り・最終結果の画面に描画エラーや文字重なりが無い。描画を繰り返しても戦闘値が変化しない。容量の最終合否は根のZIP実測13,312 bytesで判定する。
- [ ] R7（根F8）: 人間の初見/再挑戦で被弾理由を説明できるかは未実施なら未検証と記録する。自動検査やスクリーンショットの成立だけで面白さ・初見理解を合格にしない。

基準版の色以外の冗長化・範囲一致・無音での判別も継承する。主色の寄与最大やsnapshot物理分離など根1.11で次版へ送った事項を再要求しない。

### 5. 不変条件とseam

HP14・生成3連戦・同seed再挑戦・所持技1つ・威力正規化・容量を変えない。
実装は `prismatic-duel/game.js` のモノリシック基盤を継続する。
`s1.presentation-state` はduelからreadへの片方向。以下を加工せずtell/frameへ等しく継承する。

| 追加契約 | 所有と意味 | 表示上の責任 |
| --- | --- | --- |
| `lesson(m)` | duelの純関数。技から短い対処例を返す。SHOTは弾のparry対応を含む | 予告/被弾/死亡で正本の対処を使う。文言を判定に使わない |
| `feedback` | duelが更新する `{text,kind,ttl}`。kindは `hit/counter/parry/hurt/tired`、ttlは残り更新F | 成功/失敗を中央の攻防を塞がない位置で強調。ttlを描画から減らさない |
| `lastLesson` | duelが被弾時に記録する技名と対処の文字列。新戦開始で空へ。敵弾は発射時の技情報を保持し被弾した弾の情報を使う | 死亡原因をそのまま示す。現在のb.moveから推測せず、描画で初期化しない |
| `mode === "trial"` | duelが管理する安全な技試用状態。pauseから戻る先も保持する | 専用の試し場と操作案内を表示。modeや戻り先を書かない |
| `take` | `null` または `{list: Move[], i: number, held: Move, foe: {name: string, hue: number}}`。heldは撃破時の所持技、foeは撃破相手。duelは追加の退避情報を私有できる | 候補と試用中の選択を描く。HELDはtake.heldを参照しp.holdと比較しない。退避内部へ依存せず確定/カーソル更新をしない |

入力契約: bosswinは左右/A・Dで候補選択、J/Zで試用、Enterで直接確定。
trialは通常の移動・ジャンプ・攻撃キー、Rで選択へ戻る、Enterで確定。
Escape/フォーカス喪失でpause、Enter/Escapeで直前のfight/trialへ復帰する。
戻ったカーソルは保存し、試用だけではheld/run.logを更新しない。最終ボスも同じ操作でResultへ進み、確定は1回のみ記録する。
同一イベントのhurt/parryとtiredは前者優先。readはこの契約を案内へ写し、更新処理を持たない。

試用中も攻撃・移動・弾は本戦と同じ更新器を使う。標的は攻撃せず、被弾で結果画面や第2形態へ移らない。
退出時に弾・一時効果・試用状態を捨てるのはduel。戦績・次の敵・所持技の確定・ラン経過時間を汚染しない。
readはこの隔離を表示上も守り、本戦の標的を装飾で別の位置へ動かさない。
危険範囲の座標・RAIN後段・CHARGE方向は共有定義/実状態を読む。独自の当たり判定展開を作らない。

内部の `r1.screen-state` は1:1 / frame → tell。画面状態の集合へ `trial` を追加する。
title/fight/pause/dead/bosswin/resultの従来契約と描画領域/順序は継承する。
frameはduel所有modeを写すだけであり、r1がライフサイクルの書き込み権限を持つことを意味しない。
640×360・床Y=307・描画順序（背景→予告→弾→プレイヤー→ボス→効果→HUD→オーバーレイ）は共有規則として維持する。

### 6. 下位へ任せること

## 1. これは何を決めるものか

<!-- 深さ1: 課題の範囲と、それに対する解決法 -->

**課題の範囲**: `duel` が確定した状態を、**初見のプレイヤーが読める形で画面と音に出す**方法と、
それを**構造として保証する仕組み**を決める。

**含むもの**: 予告と危険範囲の描画 / 7色の語彙 / 色以外での冗長化 /
プレイヤー・ボス・弾・効果の描画 / HUD / 画面遷移と結果表示 / 音 /
`index.html` と CSS と起動（シェル）。

**含まないもの**: 何が起きるか（`duel` の担当）/ 当たり判定（同）/ 具体的な色値と座標（深さ2以降へ委任）。

### 解決法: 「描くために計算しない」

根の不変条件8 は「予告した危険範囲と実際の当たり判定は、同一の定義から作る」と定める。
**`read` の解決法は、これを「`read` は一切計算しない」という形で実効化する。**

| 層 | `read` の役割 |
| --- | --- |
| **危険範囲** | `s1` が**展開済みの矩形**を運ぶ。`read` は座標をそのまま塗る |
| **発生時刻** | `s1` が残りフレームを運ぶ。`read` は充填率に写すだけ |
| **特性** | `s1` が特性ベクトルを運ぶ。`read` は色に写すだけ |
| **回答手段** | `s1` が宣言を運ぶ。`read` は形と高さで示すだけ |

**`read` が独自に持つのは「写し方」だけで、「値」は1つも持たない。**

> 🧭 **これが `read` の設計の全部である。**
> 表示用の形を別に持った瞬間、**「見た目より判定が広い」事故**が起きうる状態になる。
> 持たなければ、起きえない。（2026-09-04）

### 3つの読み筋を同時に出す（根の 1.1）

根の 1.1 は、予備動作が始まったとき**「どこが危険か」と「いつ発生するか」が同時に出る**
ことを要求する。`read` はこれを**3つの独立した手がかり**として設計する。

| 手がかり | 何を示すか | 色を使うか |
| --- | --- | --- |
| **半透明の矩形** | **どこが**危険か | 使わない（形だけで分かる） |
| **不透明度の充填** | **いつ**発生するか | 使わない（濃さだけで分かる） |
| **色** | **何が**来るか（特性） | 使う |

**3つのうち2つは色を使わない。**これが根の不変条件11（色だけに依存させない）の実効化である。

### 姿から性格を推測させる（根の 1.1 の1行目）

戦闘が始まる前に、**ボスの姿だけで**次が読める。

| --- | --- |

| 武器シルエットの**長さ** | 射程 |
| **主色** | 最も危険度へ寄与した特性 |
| **緑の輪郭**の有無 | 防御能力 |

**見た目が生成結果の関数になっている**（根の 1.6）ので、色は飾りではなく読める情報になる。

## 2. なぜ要るのか

**今どうなっているか**: `duel` は「この技はジャンプで越えられる」と宣言し、
生成時に検査までする。しかし**プレイヤーにそれが伝わらなければ、宣言は存在しないのと同じ**である。

**何が困るか**: 伝わらないと、**プレイヤーは観察ではなく反射で対処する。**
そうなると根の 1.9 の2点（初見では緊張し一度見れば理解できる／
再挑戦で乱数ではなく学習によって勝率が上がる）が両方とも成立しない。
**`duel` がどれだけ公平に生成しても、`read` が落とせばゲームは理不尽になる。**

**とくに初見が効く。**審査員は説明を読まず、数十秒で閉じる（根の 3）。
**「なぜ負けたかを自分の言葉で言える」**（受け入れ条件「初見」）は、
負けた瞬間に**何が来ていたか見えていた**ことを要求する。

### 他の切り方との比較

- **描画 / 音 / シェルの3子案**: 却下。音とシェルが小さすぎて、

- **予告 / それ以外の2子案**: 却下。予告と「プレイヤーとボスの描画」は
  **同じ画面・同じ描画順序・同じ色の語彙**を共有するので、
  切ると共有状態が seam になって増える。`tell` にまとめた
- **`s1` の区分ごとに切る案**（技表示 / 戦闘状態 / ライフサイクル / 結果表示）: 却下。
  **入力の形で切っている**のであって、解決法の分割になっていない

### この提案自体への疑い

1. **`tell` に受け入れ条件が5つ集中している。**`frame` は2つ（うち1つは共同）。
   **`read` の重みが `tell` に寄っている**のは事実で、
   容量の配分（4,600 / 4,500）とは釣り合っていない
2. **`frame` がシェルとビルドを持つのは、描画とは性質が違う。**
   `index.html` / CSS / `build.mjs` は「画面の枠」というより「提出物の器」である。
   根が `ship` を畳んだときにここへ降りてきたもので、**押し込んだ感がある**
3. **`s1` を両子が直接読む形は、共有状態である。**読み取り専用なので争いは起きないが、
   **`s1` の形が変わると2子とも失効する**（`harness/README.md` の失効表）
4. **描画順序を親に置いたが、これは実質的に `frame` の仕事に近い。**
   親に置いたのは逆向き seam を避けるためで、**所有の自然さでは選んでいない**
