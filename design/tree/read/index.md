## 1. これは何を決めるものか

<!-- 深さ1: 課題の範囲と、それに対する解決法 -->

**課題の範囲**: `duel` が確定した状態を、**初見のプレイヤーが読める形で画面と音に出す**方法と、
それを**構造として保証する仕組み**を決める。

**含むもの**: 予告と危険範囲の描画 / 7色の語彙 / 色以外での冗長化 /
プレイヤー・ボス・弾・効果の描画 / HUD / 画面遷移と結果表示 / 音 /
`index.html` と CSS と起動（シェル）。

**含まないもの**: 何が起きるか（`duel` の担当）/ 当たり判定（同）/ 具体的な色値と座標（深さ2以降へ委任）。

### 解決法: 「描くために計算しない」

根の不変条件8 は「予告した危険範囲と実際の当たり判定は、同一の定義から作る」と定める。
**`read` の解決法は、これを「`read` は一切計算しない」という形で実効化する。**

| 層 | `read` の役割 |
| --- | --- |
| **危険範囲** | `s1` が**展開済みの矩形**を運ぶ。`read` は座標をそのまま塗る |
| **発生時刻** | `s1` が残りフレームを運ぶ。`read` は充填率に写すだけ |
| **特性** | `s1` が特性ベクトルを運ぶ。`read` は色に写すだけ |
| **回答手段** | `s1` が宣言を運ぶ。`read` は形と高さで示すだけ |

**`read` が独自に持つのは「写し方」だけで、「値」は1つも持たない。**

> 🧭 **これが `read` の設計の全部である。**
> 表示用の形を別に持った瞬間、**「見た目より判定が広い」事故**が起きうる状態になる。
> 持たなければ、起きえない。（2026-09-04）

### 3つの読み筋を同時に出す（根の 1.1）

根の 1.1 は、予備動作が始まったとき**「どこが危険か」と「いつ発生するか」が同時に出る**
ことを要求する。`read` はこれを**3つの独立した手がかり**として設計する。

| 手がかり | 何を示すか | 色を使うか |
| --- | --- | --- |
| **半透明の矩形** | **どこが**危険か | 使わない（形だけで分かる） |
| **不透明度の充填** | **いつ**発生するか | 使わない（濃さだけで分かる） |
| **色** | **何が**来るか（特性） | 使う |

**3つのうち2つは色を使わない。**これが根の不変条件11（色だけに依存させない）の実効化である。

### 姿から性格を推測させる（根の 1.1 の1行目）

戦闘が始まる前に、**ボスの姿だけで**次が読める。

| 見た目 | 示すもの |
| --- | --- |
| 武器シルエットの**太さ** | 威力 |
| 武器シルエットの**長さ** | 射程 |
| **主色** | 最も危険度へ寄与した特性 |
| **緑の輪郭**の有無 | 防御能力 |

**見た目が生成結果の関数になっている**（根の 1.6）ので、色は飾りではなく読める情報になる。

### 実装済みのものとの関係

`prismatic-duel/` に**既に対応物がある**（[`design/AS_BUILT.md`](../AS_BUILT.md)）。

| `read` の担当 | 実装の対応 | 状態 |
| --- | --- | --- |
| 予告と危険範囲 | `drawTelegraph()` / `attackColor()` | **動いている。`moveRect()` を判定と共有** |
| 描画 | `drawPerson()` / `drawBoss()` / `background()` | **動いている。ただし3人ぶんの控え描画がある** |
| HUD | `hud()` / `bar()` | **動いている。ただし3人ぶんのバーがある** |
| 画面遷移 | `step()` / `overlay()` / `draw()` | **動いている** |
| 音 | `sound()` / `wakeAudio()` | **動いている。Web Audio のオシレータのみ** |
| シェル | `index.html` / `style.css` / `build.mjs` | **動いている。ZIP 8,918 bytes** |

**`read` の実装も、ゼロからではなく差分から始まる。**

## 2. なぜ要るのか

**今どうなっているか**: `duel` は「この技はジャンプで越えられる」と宣言し、
生成時に検査までする。しかし**プレイヤーにそれが伝わらなければ、宣言は存在しないのと同じ**である。

**何が困るか**: 伝わらないと、**プレイヤーは観察ではなく反射で対処する。**
そうなると根の 1.9 の2点（初見では緊張し一度見れば理解できる／
再挑戦で乱数ではなく学習によって勝率が上がる）が両方とも成立しない。
**`duel` がどれだけ公平に生成しても、`read` が落とせばゲームは理不尽になる。**

**とくに初見が効く。**審査員は説明を読まず、数十秒で閉じる（根の 3）。
**「なぜ負けたかを自分の言葉で言える」**（受け入れ条件「初見」）は、
負けた瞬間に**何が来ていたか見えていた**ことを要求する。

- **色覚特性のあるプレイヤー**。不変条件11 が直接効く

## 4. 終わったとどうやって分かるか（受け入れ条件）

親から `テーマ`・`初見（主）`・`学習（前提）` を割り当てられた。

- [ ] **予告と判定が一致する**（不変条件8・親条件「学習」の前提）:
      **画面に描いた危険範囲の座標が、`s1` が運んできた値とビット単位で同一。**
      判定: 全フレームで描画に渡した矩形と `s1` の値を比較し、**差異0件。**

- [ ] **色を取り除いても遊べる**（不変条件11・親条件「初見」の一部）:

      「どこが危険か」「いつ発生するか」が読める。**

      **被弾回数がカラー版の 1.5倍以内**に収まること

      > 🧭 **「色以外でも同じ情報を示す」を、実際に色を消して測る形にした。**

- [ ] **テーマ**（親条件そのまま・担当は `read`）:

- [ ] **知覚の下限の検証**（親に残すもの4・`read` の担当）:

## 5. 変えてはいけない前提

**根から継承**（`root@2026-09-04-decision-7` / 親からの振り分け）

6. **容量の目安 9,500 inlined bytes**（シェルを含む）

**逆向きの seam は無い。**`tell` は `frame` へ何も返さない。

### この提案自体への疑い

1. **`tell` に受け入れ条件が5つ集中している。**`frame` は2つ（うち1つは共同）。
   **`read` の重みが `tell` に寄っている**のは事実で、
   容量の配分（4,600 / 4,500）とは釣り合っていない
2. **`frame` がシェルとビルドを持つのは、描画とは性質が違う。**
   `index.html` / CSS / `build.mjs` は「画面の枠」というより「提出物の器」である。
   根が `ship` を畳んだときにここへ降りてきたもので、**押し込んだ感がある**
3. **`s1` を両子が直接読む形は、共有状態である。**読み取り専用なので争いは起きないが、
   **`s1` の形が変わると2子とも失効する**（`harness/README.md` の失効表）
4. **描画順序を親に置いたが、これは実質的に `frame` の仕事に近い。**
   親に置いたのは逆向き seam を避けるためで、**所有の自然さでは選んでいない**
