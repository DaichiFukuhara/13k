## 1. これは何を決めるものか

**いつ、どんな音を、どう作るか。**

### 1.1 作り方（不変条件12 の実効化）

**Web Audio のオシレータ1つ ＋ ゲイン1つを、鳴らすたびに作って捨てる。**

- 波形（矩形波 / 三角波 / のこぎり波 / 正弦波）を選ぶ
- 周波数を設定し、**指数的に下げる**（0.65倍まで）
- 音量を設定し、**指数的に落とす**（ほぼ0まで）
- 再生し、指定時間で止める

**音声ファイルを持たない。外部ライブラリを持たない。**
**出所は実装**（`sound()`）。[`design/AS_BUILT.md`](../../../../AS_BUILT.md) §7。

### 1.2 鳴らすもの（`s1` のライフサイクルイベント）

| イベント | 波形 | 高さ | 長さ |
| --- | --- | --- | --- |
| プレイヤーの攻撃 | 矩形波 / のこぎり波 | 中 | 短い |
| ジャンプ | 正弦波 | 中低 | 短い |
| ローリング | 正弦波 | 低 | 短い |
| パリィ開始 | 三角波 | 中高 | 極短 |
| **パリィ成功** | **矩形波** | **高い（1100Hz）** | 中 |
| 被弾 | のこぎり波 | **低い（75Hz）** | 長め |
| ボスの弾 | のこぎり波 | 低 | 中 |
| **体勢崩し** | 矩形波 | **高い（880Hz）** | 長め |
| 撃破 | のこぎり波 | **最低（70Hz）** | **最長** |

**高い音＝プレイヤーに良いこと、低い音＝悪いこと**という一貫した対応がある。

### 1.3 情報の主経路にしない（`read` の不変条件10）

**音が示すものは、すべて画面でも示されている。**

| 音が示すもの | 画面での対応 | 担当 |
| --- | --- | --- |
| パリィ成功 | 白い火花 ＋ 「PARRY」の表示 ＋ ボスが `recover` へ | `tell` / `hud` |
| 被弾 | 画面揺れ ＋ 火花 ＋ **HP バーが減る** | `tell` / `hud` |
| 体勢崩し | ボスが傾く ＋ 大きな火花 ＋ **体勢バーが0** | `tell` / `hud` |
| 撃破 | 撃破画面へ遷移 | `screens` |

**音は「速い」だけで、「唯一」ではない。**

> 🧭 **大会のプレイヤーは音を出さないことがある。**
> 審査員が複数の作品を並べて見るとき、音は切られていることが多い。
> **音に情報を載せると、その状況で作品が壊れる。**（2026-09-04）

### 1.4 起動（ブラウザの制約）

**ブラウザは、ユーザー操作の前に音を鳴らすことを許さない。**
最初のキー入力で音の文脈を作り、停止していれば再開する。

**音が使えない環境でも、ゲームは通常どおり動く。**

## 2. なぜ要るのか

**手触りのため。**パリィが成功したとき、画面の変化だけでは「効いた」感覚が薄い。
**高い音が1つ鳴るだけで、成功が身体に届く。**

根の 1.9 の1点目（初見では緊張し、一度見れば理解できる）は、
**緊張と理解の両方が体験の質に依存する。**音はそこに効く。

**同時に、音は最も削りやすい。**700 bytes は `read` の 7% だが、
容量が足りなくなったとき最初に候補になる。
**だから「切っても読める」ことを最初から条件にする。**

## 3. 誰が使い、誰が影響を受けるか

- **プレイヤー**。音を出している人にだけ届く
- **音を切っている審査員**。**この人たちのために不変条件10 がある**
- **制作者本人**: 容量が足りないとき、ここが最初に削られる

## 4. 終わったとどうやって分かるか（受け入れ条件）

- [ ] **音を切っても全部読める**（主担当）:
      **音量0で通しプレイして、被弾が音あり版の 1.2倍以内。**
      判定: 音なしで1体目を通す。ブラウザのタブミュートで測る

- [ ] **1.3 の表に穴が無い**:
      **音が示すものすべてに、画面での対応がある。**
      判定: 表を読んで空欄が0件。加えて**各対応が実際に実装されている**ことを確認

      > 🧭 **`palette` の冗長化の表（同ノード 1.4）と同じ形にした。**
      > 「切っても読める」は通った / 通らないしか分からないので、
      > **どの音に画面の対応が無いかを表で特定する。**（2026-09-04）

- [ ] **音声ファイルを持たない**（不変条件12・「外部リソースに依存しない」の分担）:
      判定: ビルド成果物に音声のバイナリが0件。
      音がすべて Web Audio のオシレータで生成されていること

- [ ] **音が使えなくても動く**:
      **音の文脈が作れない環境でも、ゲームが通常どおり動く。**
      判定: 音の生成を強制的に失敗させ、例外もフリーズも起きないこと

- [ ] **容量**: **700 inlined bytes 以内**

## 5. 変えてはいけない前提

1. 根の不変条件 **12**（音声ファイル・外部ライブラリを持たない。**音は実行時に生成する**）
2. **音は情報の主経路にしない。音を切っても全部読める**（`read` の不変条件10）
3. **`s1` を読むだけ。書き換えない**
4. **音の失敗でゲームを止めない**

## 6. 決めないこと・任せること

**実装が決めてよい**

- 波形・周波数・長さ・音量のすべて（実装値は 1.2 の表）
- 音を鳴らすイベントを増やす・減らすこと（**1.3 の表に対応を書くこと**が条件）
- フィルタやエンベロープを足すこと（容量の範囲内で）
- BGM を作るかどうか（**容量的にほぼ不可能だが、禁止はしない**）

**今回は決めない**

- 音声ファイルを持つこと
- 音量調整 UI（`frame` の 6 で「設定 UI は作らない」）

## 7. 分からないこと・仮置きしていること

1. **受け入れ条件が「音の不在に耐えること」しか測っていない。**
   **音そのものが良いかを測る条件が無い**（`frame` の分割提案の疑い2 が自認）。

   **これは意図的である。**「良い音」は検査可能な形にできず、
   `precedents.md` 2026-08-25「満足できたら終了は判定不能として却下」に抵触する。
   **ただし、条件が全部通っても音が不快である可能性は残る。**
   仮置き: 制作者の主観で判断する。`provisional: true`

2. **「音あり版の 1.2倍以内」の閾値に根拠が無い。**
   `palette` のグレースケール検査（1.5倍）より厳しくしたのは、
   **音のほうが情報量が少ないはず**という想定に基づく。実測していない

3. **音を「切る」手段が実装に無い**（`frame` の 7-4 から引き継ぎ）。
   タブミュートで測るが、**製品に設定 UI は作らない。**
   プレイヤーがブラウザ側で切ることを前提にしている

4. **容量が足りなくなったとき、ここが最初に削られる。**
   700 bytes を全部落としても**受け入れ条件は全部通る**（音が無くても読めるので）。
   **これは設計として正しいが、削る判断が容易すぎるとも言える**
