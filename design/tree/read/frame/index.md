### 1. 決めるもの

開始前から「敵を倒し、技を1つ奪い、試して次へ進む」目的を示す。
戦闘中はゲージの役割と攻撃色の意味を短い文字で補い、反撃できる窓と実際の反撃成功を区別する。
被弾の原因・スタミナ不足・パリィ成功を読み分けられるようにする。
撃破後は候補の実際の間合い/発生/段数/消費を直感的な説明と試用で理解できるようにする。
描画と案内の詳細化だけを行い、入力、試用状態、戦績、ゲーム進行はduelが所有する。

### 2. なぜ要るか

無名の細いバーや色だけでは、残り体力と行動資源、次に攻めてよい時機を判断しにくい。
最初の撃破まで技奪取が分からず、数値だけの候補画面では使用感を想像しにくかった。
被弾した技と次に試す対処が残れば、同じ相手への再挑戦が学習につながる。

### 3. 利用者

Desktopで初めて遊ぶ人と、すぐ再挑戦・次戦へ進みたい経験者。
試用は任意で、Enterによる直接確定を維持する。説明画面を追加して進行を止めない。

### 4. 受け入れ条件

- [ ] FR1（R1/F1・hud）: ボスHPとPOSTURE、プレイヤーHPとSTが文字・位置・太さで識別できる。所持技と消費STが試用中も実状態と一致する。
- [ ] FR2（R1/R3・hud）: 7色の意味を短く読める。実際のrecover/stagger時に反撃窓を示し、成功は `feedback.kind === "counter"` のイベントからのみ表示する。
- [ ] FR3（R3/R4・hud）: `feedback` のhit/counter/parry/hurt/tiredを文字でも識別できる。tiredはST不足、hurtは原因と対処を示す。中央の攻防、ゲージ、既存メッセージを重ねない。
- [ ] FR4（R1/R4・screens）: タイトルで「倒した敵の技を1つ奪える」を読め、通常操作を確認できる。死亡時は `lastLesson` を示し、現在の技から原因を推測しない。
- [ ] FR5（R5・screens）: 候補の短い使用感、左右/A・D選択、J/Z試用、Enter確定を読める。HELDは `take.held`、撃破相手の名前/色は `take.foe` を参照する。
- [ ] FR6（R5/R6・screens）: 試用画面に試用中の表示、通常操作、Rで候補へ戻る、Enterで次へ、Escでpauseを示す。最終撃破後の確定先が結果だと分かり、結果の3体/奪取技/戦績表示が保たれる。
- [ ] FR7（R6/F7・両葉）: title/fight/dead/bosswin/trial/pause/resultで描画エラーと文字重なりがない。描画を繰り返しても戦闘/選択/経過時間/feedback.ttl等が変わらない。全体ZIP 13,312 bytesの実測は根へ返す。
- [ ] FR8（R7/F8）: 人間の初見理解・面白さは未実施なら未検証。自動検査や画面成立だけで合格にしない。

### 5. 継承制約と公開契約

640×360、床Y=307、単独プレイヤーHP14、生成3連戦、同seed再挑戦、所持技1つと威力正規化を維持する。
描画順序は背景→予告→弾→プレイヤー→ボス→効果→HUD→オーバーレイ。
文字で色を冗長化し、無音でも必要情報を失わせない。外部画像・音声・フォント・ライブラリは増やさない。

| 読み取り契約 | frameでの扱い |
| --- | --- |
| `lesson(m)` | duel所有の純関数。技から短い対処例を返す。SHOTの弾パリィ対応を含み、不可を可能と書き換えない。対処は安全保証にしない |
| `feedback` | duel所有 `{text,kind,ttl}`。kindはhit/counter/parry/hurt/tired、ttlは残り更新F。hudが表示し、消費/減衰/競合優先度を描画で更新しない |
| `lastLesson` | duelが被弾時に記録した技名と対処の文字列。敵弾は発射時の技由来。死亡表示に使い、現在のb.moveを原因として推測しない |
| `mode === "trial"` | duel所有の安全な試用。frameがmodeを読み、r1.screen-stateの画面集合にもtrialを含める。pauseの戻り先もduel所有 |
| `take` | nullまたは `{list: Move[], i: number, held: Move, foe: {name: string, hue: number}}`。HELDの比較元は撃破時のtake.held、相手表示はtake.foe。試用で変わるp.hold/bを撃破記録の代用にしない。duel私有の退避情報を読まない |

bosswin: 左右/A・Dで選択、J/Zで試用、Enterで直接確定。
trial: 通常の移動・ジャンプ・攻撃キー、Rで選択へ戻る、Enterで確定。
Escape/フォーカス喪失でpause、Enter/Escapeで直前のfight/trialへ復帰する。
戻ったカーソルは保持され、試用だけではheld/run.log/ラン経過時間/次の敵を変更しない。
最終ボスも同じ操作で結果へ進む。確定を一度だけ記録するのはduel。
同一イベントのhurt/parryとtiredの優先はduelの前者優先に従う。

試用標的は攻撃しない。被弾で結果や第2形態へ進まず、通常戦と同じ攻撃/弾更新器の実状態を描く。
位置・当たり判定・予告の共有定義はtellが描く。screensはtell所有描画関数を呼び、標的座標を書かない。
既存drawのshake減衰も描画から除く。必要な更新側への移管はduel/runtime所有者へ依頼する。

7色の語彙は赤=高威力、橙=長持続・残留、黄=短い予備動作、緑=防御、青=長射程、藍=追尾、紫=多段・特殊変化。
攻撃色と成功/失敗表示を混同させず、feedbackは必ず文字を併用する。
ゲージ/凡例/feedbackの配置はhud、操作案内の文字列はscreensが唯一所有する。
hudから操作案内が必要でも二重にキー文字列を追加せず、screensの描画段階で提示する。

### 6. 葉へ任せるもの

hudはHP/ST/POSTUREラベル、反撃窓の短い文言、feedbackの強弱、7色凡例の具体的な配置を決める。
screensはタイトル、死亡lesson、候補の短い説明、試用操作、最終確定/結果の文言と配置を決める。
通常キーは現行runtimeと照合する。操作案内はscreensの一箇所で所有しshellを変更しない。
容量が厳しければ装飾を削り、ゲージ識別・理由・試用操作を優先する。
両葉は描画専用補助を自分の所有関数の近傍に追加可能。共有の補助関数を同時編集しない。

### 7. 未確定・限界

文字の最終配置と長文の収まりは実画面で検証する。人間の初見理解は別の未検証条件。
基準版のinlined目安は増設分の実測前であり、合否は根のZIP上限で判定する。
公開入力不足、描画状態の更新移管、他葉関数変更が必要ならframeへboundary_requestを返す。

## 1. これは何を決めるものか

**戦闘画面の外側すべて。**情報の提示・画面の行き来・音・そして**提出物の器。**

### 機能の一覧（これが深さ3の子になる）

| 機能 | 中身 |
| --- | --- |
| **HUD** | 戦闘中に出す情報（ボス HP・体勢・名前 / プレイヤー HP・スタミナ / **所持技** / シード / 技名） |
| **画面遷移** | タイトル・戦闘・ポーズ・敗北・**撃破（奪取の選択を兼ねる）**・結果。**入力の受付と提示** |
| **音** | Web Audio のオシレータで実行時に生成する効果音 |
| **シェル** | `index.html` / CSS / 起動 / **ビルドが提出物を作ること** |

### 構造: 4子は互いを知らない

```
   s1.presentation-state ──┬──► hud      （戦闘中の情報）
   （親が加工せず渡す）      ├──► screens  （画面の行き来）
                            ├──► sound    （音）
                            └──► shell    （器とビルド）
```

**子同士の seam が1本も無い。**4子とも `s1` と親の定数だけを読む。
**操作説明の所有者は `screens` に固定した**（親に残すもの6。`shell` は場所だけ用意する）。

**`r1.screen-state` を `tell` へ渡すのは `screens` の決定に基づくが、
`frame` の代表として親が権威化して降ろす**（親に残すもの5）。

### 1.1 「器」がここにあることについて

**`shell`（`index.html` / CSS / ビルド）は、描画とは性質が違う。**
根が `ship` を子ではなく親へ畳んだとき（案 B・2026-09-01）、
容量の受け皿として `read` の 9,500 bytes に**シェルを含めた**ため、ここへ降りてきた。

**押し込んだ感がある**ことは `read` の分割提案が自認している（`read-split-1` の疑い2）。
**ただし置き場所としては他に無い** — `duel` は戦闘の中身しか持たない。

## 2. なぜ要るのか

**受け入れ条件「初見」は、予告が読めるだけでは満たせない。**
根の 4 は「**説明文を読まずに操作を理解し**、最初の敗北まで到達し、
**なぜ負けたかを自分の言葉で言える**」と定める。

| 要求 | 担当 |
| --- | --- |
| 説明文を読まずに**操作を理解する** | **`screens`**（タイトルと画面上の提示） |
| 最初の**敗北まで到達する** | `tell`（予告が読める）＋ **`hud`**（残り HP が見える） |
| **なぜ負けたかを言える** | `tell`（何が来ていたか）＋ **`screens`**（敗北画面の情報） |

**そして「提出可能」は `shell` が無いと存在しない。**
根は「提出可能」を `deferred` にしているが、
**`shell` はその `deferred` が解除されたとき最初に必要になるノード**である。
