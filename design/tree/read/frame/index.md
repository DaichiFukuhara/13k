## 1. これは何を決めるものか

**戦闘画面の外側すべて。**情報の提示・画面の行き来・音・そして**提出物の器。**

### 機能の一覧（これが深さ3の子になる）

| 機能 | 中身 |
| --- | --- |
| **HUD** | 戦闘中に出す情報（ボス HP・体勢・名前 / プレイヤー HP・スタミナ / **所持技** / シード / 技名） |
| **画面遷移** | タイトル・戦闘・ポーズ・敗北・**撃破（奪取の選択を兼ねる）**・結果。**入力の受付と提示** |
| **音** | Web Audio のオシレータで実行時に生成する効果音 |
| **シェル** | `index.html` / CSS / 起動 / **ビルドが提出物を作ること** |

### 構造: 4子は互いを知らない

```
   s1.presentation-state ──┬──► hud      （戦闘中の情報）
   （親が加工せず渡す）      ├──► screens  （画面の行き来）
                            ├──► sound    （音）
                            └──► shell    （器とビルド）
```

**子同士の seam が1本も無い。**4子とも `s1` と親の定数だけを読む。
**操作説明の所有者は `screens` に固定した**（親に残すもの6。`shell` は場所だけ用意する）。

**`r1.screen-state` を `tell` へ渡すのは `screens` の決定に基づくが、
`frame` の代表として親が権威化して降ろす**（親に残すもの5）。

### 1.1 「器」がここにあることについて

**`shell`（`index.html` / CSS / ビルド）は、描画とは性質が違う。**
根が `ship` を子ではなく親へ畳んだとき（案 B・2026-09-01）、
容量の受け皿として `read` の 9,500 bytes に**シェルを含めた**ため、ここへ降りてきた。

**押し込んだ感がある**ことは `read` の分割提案が自認している（`read-split-1` の疑い2）。
**ただし置き場所としては他に無い** — `duel` は戦闘の中身しか持たない。

## 2. なぜ要るのか

**受け入れ条件「初見」は、予告が読めるだけでは満たせない。**
根の 4 は「**説明文を読まずに操作を理解し**、最初の敗北まで到達し、
**なぜ負けたかを自分の言葉で言える**」と定める。

| 要求 | 担当 |
| --- | --- |
| 説明文を読まずに**操作を理解する** | **`screens`**（タイトルと画面上の提示） |
| 最初の**敗北まで到達する** | `tell`（予告が読める）＋ **`hud`**（残り HP が見える） |
| **なぜ負けたかを言える** | `tell`（何が来ていたか）＋ **`screens`**（敗北画面の情報） |

**そして「提出可能」は `shell` が無いと存在しない。**
根は「提出可能」を `deferred` にしているが、
**`shell` はその `deferred` が解除されたとき最初に必要になるノード**である。

## 3. 誰が使い、誰が影響を受けるか

- **審査員・投票者**。タイトル画面で操作が分からなければそこで閉じる
- **`tell`**: `r1` で画面状態と描画領域を受ける
- **制作者本人**: `shell` のビルドが**毎回 ZIP サイズを出す。**
  受け入れ条件「提出可能」の唯一の観測点
- **将来の実装者**: `frame` は削る余地が最も大きい（音・演出・画面の文言）

## 4. 終わったとどうやって分かるか（受け入れ条件）

- [ ] **初見（操作の提示と結果表示）**:
      **説明文を読まずに操作を理解できる。**
      判定: 制作者以外の1人にタイトル画面だけを見せ、
      **移動・ジャンプ・攻撃・パリィ・ロールの5つを説明なしに操作できる**こと

- [ ] **色を取り除いても遊べる（HUD の色）**:
      グレースケール版で、**ボス HP と体勢、プレイヤー HP とスタミナを見分けられる。**
      判定: 4本のバーが**位置と形**で区別できること（色だけで区別していない）

- [ ] **音を切っても全部読める**（`read` の不変条件10）:
      **音量0で通しプレイして、被弾がカラー音あり版の 1.2倍以内。**
      判定: 音なしで1体目を通す

- [ ] **提出可能**（根の受け入れ条件。`shell` が実行主体）:
      `dist/` の ZIP が **13,312 bytes 以下**であり、展開して `index.html` を
      ブラウザで開くだけで、**ネット接続なしに遊べる。**
      判定: ビルドが毎回サイズを表示し、**オフラインの実機で1回通す**

      > **2026-09-04 時点の実測: ZIP 8,918 bytes（上限の 67.0%・余裕 4,394 bytes）。**
      > **既に通っている**（[`design/AS_BUILT.md`](../AS_BUILT.md) §0）

- [ ] **外部リソースに依存しない**（根の 5-A-2）:
      判定: ビルド成果物が `index.html` 1枚だけで、
      CDN・外部画像・外部フォント・外部API への参照が0件

- [ ] **容量**: `frame` 由来が **4,500 inlined bytes 以内**（シェルを含む）

## 5. 変えてはいけない前提

1. 根の不変条件12件。とくに
   - **11** 色だけに依存させない
   - **12** 画像・音声ファイル・外部ライブラリを持たない。**描画と音は実行時に生成する**
2. **音は情報の主経路にしない**（`read` の不変条件10）。**音を切っても全部読める**
3. **`s1` を読むだけ。書き換えない**
4. **7色の語彙**（`read` の表）
5. **内部解像度 640×360**（同 5）
6. **ビルドの仕様**（根の親に残すもの10）:
   **inlined と ZIP の両方を毎回表示し、13,312 超で終了コード1**
7. **16:9 の1画面固定。スクロールしない**（根の 1.7）
8. **ビルドは提出物ではなく道具なので、容量に含めない**（根の親に残すもの10）

## 6. 決めないこと・任せること

**深さ3または実装が決めてよい**

- HUD の配置と何を出すか（実装は上端にボス、下端にプレイヤー）
- 画面の文言とレイアウト
- 音の作り方（Web Audio の範囲内で自由）
- CSS のレイアウト（実装は grid で中央寄せ・`aspect-ratio: 16/9`）

**今回は決めない**

- 設定画面、音量調整 UI、多言語対応
- 画像・音声ファイルを持つこと

## 7. 分からないこと・仮置きしていること

1. **交代を削ると HUD が変わる**（`read` の 7-4 から引き継ぎ）。
   実装は3人ぶんの HP・スタミナバーを下端に置いている。
   1人になると**画面下部が空く。**
   仮置き: バーを1組だけ残し、余白は空けたままにする。`provisional: true`

2. **容量 4,500 bytes にシェルとビルドを含めて収まるか未検証。**
   実装の `index.html` ＋ `style.css` は小さい（合わせて 1KB 未満）が、
   **画面遷移のオーバーレイと文言が意外に大きい。**

3. **「初見（操作の提示）」の判定に被験者が要る**（根の 7-2）。
   確保できない場合の代替が無い

4. **音を「切る」手段が実装に無い。**受け入れ条件「音を切っても全部読める」を
   測るには、音量0にする手段が要る。
   仮置き: ブラウザのタブミュートで測る。**製品に設定 UI は作らない**（6 で決めない）

   線が2本になるので避けたが、**実装では同じ関数呼び出しになる**
4. **子が4つで、`read` 側の深さ3が計7ノードになる**（`tell` 3 ＋ `frame` 4）。
   `duel` 側は6ノード（`gen` 3 ＋ `fight` 3）。
