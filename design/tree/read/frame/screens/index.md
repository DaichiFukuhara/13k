## 1. これは何を決めるものか

**画面の状態と、その行き来。**そして**説明文なしで操作を伝える方法。**

### 1.1 画面の状態

```
title ──Enter──► fight ──撃破──► bosswin ──Enter──► fight（次のボス）
  ▲                │                                    │
  │                ├──敗北──► dead ──Enter/R──► fight（同じ敵）
  │                │                └──N──► title（新シード）
  │                └──Esc──► pause ──Enter/Esc──► fight
  │
  └──Enter/N── result ◄──3体目の撃破──
```

| 状態 | 出すもの |
| --- | --- |
| `title` | タイトル・**7色の帯**・シード・**操作の提示** |
| `fight` | 戦闘（`tell` が描く）＋ HUD（`hud` が描く） |
| `pause` | 「一時停止」と復帰方法 |
| `dead` | **ボスの異名**・「同じ敵へ再挑戦」・「新しいシード」 |
| `bosswin` | 撃破の表示・**奪取の選択**（1.10）・次へ進む案内 |
| `result` | **タイム・被弾数・パリィ数・シード**・再走と新ランの案内 |

**出所は実装**（`step()` / `overlay()` / `draw()`）。
[`design/AS_BUILT.md`](../../../../AS_BUILT.md) §7。

### 1.2 説明文なしで操作を伝える（受け入れ条件「初見」の本体）

**根の 4 は「説明文を読まずに操作を理解し」と定める。**
**「説明文を読まない」のであって「何も出さない」ではない。**

| 手段 | 内容 |
| --- | --- |
| **タイトル画面の1行** | 「ENTER BEGIN　N NEW SEED」— **今押せるキーだけ**を出す |
| **HTML の下に常時表示** | 「MOVE A/D　JUMP W/Space　ATTACK J/Z　PARRY K/X　ROLL L/C」 |
| **`s1` の操作割当を使う** | キー割り当ては `duel` が持つ。**`screens` は写すだけ** |

> 🧭 **「今押せるキーだけを出す」のが要点である。**
> タイトルで全操作を並べると読まれない。
> **戦闘に入る前に必要なのは「始め方」だけ。**
> 戦闘の操作は**Canvas の外（HTML の段落）に常時置く**ので、
> 「説明文を読む」動作を要求しない。（2026-09-04・実装から）

### 1.2.1 撃破画面は奪取の選択を兼ねる（根の 1.10）

**根の 1.1 の7は「撃破後にシードと技構成が表示される」と定めている。**
**そこがそのまま選択画面になる。**画面を1つ増やさない。

| 出すもの | 何のためか |
| --- | --- |
| 倒したボスの**全技**（4〜5個）＋ **今の所持技** | 選択肢。`s1` の「奪取の候補」から |
| 各技の **形状名 / 射程 / 予備動作 / 硬直 / 多段 / 色** | **威力は出さない**（正規化されて全部同じなので、出すと誤解を生む） |
| **スタミナ消費** | 速い技ほど高い。**代償が見える**ようにする |
| どれが今の所持技か | 「持ち替えない」を選べることが分かるように |

**選ぶまで次へ進めない。**左右で選び、決定キーで確定する。

> 🔒 **凍結（`screens@2026-09-05-decision-5`）。`screens` は選択を実行しない。**
> **カーソルを動かすのも確定するのも `duel.fight.arena` である。**
> `screens` は `s1` の「奪取の候補」と「奪取のカーソル」を読んで**描くだけ。**
>
> **`read` から `duel` へ返す経路を作らない** — `s1` は片方向で、
> 逆向きは根が `split-1`〜`6` で何度も苦労して消したものである。
> 入力はもともと `duel` 側が読んでいるので、**新しい経路は要らない。**

> 🧭 **威力を出さないのが要点である。**
> 全部 7 なので、数字を並べると「どれも同じ」に見えて選ぶ意味が消える。
> **出すのは間合いと速さと代償だけ** — それが 1.10 で実際に変わるものである。（2026-09-05）

> ⚠️ **色を出すのはテーマに直接効く**（根の 1.10）。
> 7色のうちどれを持つかが見えると、「虹を集める」が体験になる。
> ただし**色だけで選ばせない** — 形状名と数値も並べる（不変条件11）。

### 1.3 「なぜ負けたか」を支える（受け入れ条件「初見」の後半）

**敗北画面で出すもの:**

| 項目 | 何のためか |
| --- | --- |
| **ボスの異名**（色名＋武器名） | 「何に負けたか」を言語化する足がかり |
| **同じ敵へ再挑戦できること** | 根の 1.8。**学習が起きる前提** |
| 新しいシードへ行けること | 詰まったときの逃げ道 |

**根の 1.9 の2点目（同じ敵への再挑戦で学習によって勝率が上がる）は、
再挑戦が1キーでできることに依存する。**

### 1.4 結果表示（根の 1.1 の7番目）

**撃破後にシードと技構成が表示される。**

- **シード**（36進6桁）— 同じ敵を再現できる
- タイム・被弾数・パリィ数 — **学習の指標**
- 再走（同じシード）と新ラン

**「同じシードは同じ敵を再現する」（不変条件9）が、
プレイヤーから見えるのはここだけである。**

### 1.5 `r1.screen-state` の内容

**`screens` が決め、`frame` が権威化して `tell` へ降ろす。**

- 画面状態（`title` / `fight` / `pause` / `dead` / `bosswin` / `result`）
- 戦闘画面の描画領域（矩形）と内部解像度
- 描画順序のどこで `tell` が呼ばれるか

**`tell` は `fight` 以外の状態では描かない。**

## 2. なぜ要るのか

**審査員はタイトル画面で判断する。**根の 3 は
「初見・短時間・説明を読まない。作品を並べて相対比較する」と書いている。

**操作が分からなければ、ゲームの中身は評価されない。**
`duel` の公平性も `tell` の予告も、**プレイヤーが操作を始めなければ存在しない。**

## 3. 誰が使い、誰が影響を受けるか

- **審査員・投票者**。**最初に見る画面がここ**
- **`tell`**: `r1` を受けて、`fight` 状態のときだけ描く
- **リトライするプレイヤー**: 敗北 → 再挑戦の速さが学習の速さを決める
- **`hud`**: 結果表示で同じ数値を使うが、**互いを知らない**（両方 `s1` を読む）

## 4. 終わったとどうやって分かるか（受け入れ条件）

- [ ] **初見**（主担当）:
      **ルールを知らない人が、説明文を読まずに操作を理解し、最初の敗北まで到達し、
      なぜ負けたかを自分の言葉で言える。**
      判定: 根の 4「初見」のまま。制作者以外の1人にプレイさせ、
      負けた直後に口頭で理由を言わせる

- [ ] **操作の提示だけで始められる**（`初見` の `screens` 側の分担）:
      **タイトル画面だけを見せて、移動・ジャンプ・攻撃・パリィ・ロールの5つを
      説明なしに操作できる。**
      判定: 制作者以外の1人で確認。**5つとも押せること**

- [ ] **再挑戦が1キー**（根の 1.8・1.9 の2点目の前提）:
      **敗北から同じ敵への再挑戦が、1回のキー入力で始まる。**
      判定: 敗北画面から `Enter` で戦闘が始まり、**技構成が前回とバイト一致**

- [ ] **シードが見える**（不変条件9 の可視化）:
      **タイトル・戦闘中・結果のすべてでシードが読める。**
      判定: 3画面すべてに表示があること

- [ ] **画像・外部フォントを持たない**（不変条件12）:
      判定: 描画がすべて Canvas API とシステムフォントであること

- [ ] **奪取の選択が成立する**（根の 1.10）:
      **撃破画面で候補が全部見え、左右と決定だけで選べる。**
      判定: 5技のボスを倒し、**候補6つ**（ボスの5技＋今の所持技）が画面に収まり、
      **威力が表示されていない**こと。選択せずに次へ進めないこと

- [ ] **`screens` が選択を実行していない**（片方向性の保持）:
      **カーソルの状態も確定の判断も `screens` が持たない。**
      判定: `s1` の「奪取のカーソル」を読んで描くだけであることをコードで確認。
      **`read` から `duel` へ値を返すコードが1行も無いこと**

- [ ] **容量**: **1,900 inlined bytes 以内**（**奪取の選択画面を含む**）

## 5. 変えてはいけない前提

1. 根の不変条件 **9**（同じシードは同じ敵を再現する）、
   **12**（画像・外部ライブラリを持たない）
2. **`s1` を読むだけ。**キー割り当ては `duel` が持つ（`s1` の操作割当）。
   **`screens` は写すだけで、割り当てを決めない**
3. **画面領域の分割**（`frame` の親に残すもの4）
4. **`r1.screen-state` を `tell` へ直接渡さない**（同5）。`frame` が権威化する
5. **負けたら同じ敵へ即再挑戦できる**（根の 1.8）。技・数値・外見は変わらない
6. **16:9 の1画面固定。スクロールしない**（根の 1.7）

## 6. 決めないこと・任せること

**実装が決めてよい**

- 画面の文言（英語・日本語・記号のみ、どれでもよい）
- オーバーレイのレイアウトと大きさ（実装は 470×206 の暗幕）
- ポーズの有無と入力（実装は Escape ＋ フォーカス喪失で自動）
- 結果表示に何を出すか（実装はタイム・被弾・パリィ・交代数。**交代は削る**）
- タイトルの見た目（実装は7色の帯 ＋ 大きな文字）
- 遷移のアニメーション（無しでよい）

**今回は決めない**

- 設定画面、多言語対応、キーコンフィグ
- セーブ機能、ランキング

## 7. 分からないこと・仮置きしていること

1. **結果表示から「交代数」を削ると、指標が3つになる**（タイム・被弾・パリィ）。
   **被弾が「学習」の指標**（根の受け入れ条件）なので必須。
   仮置き: 3つのまま。`provisional: true`

2. **「操作の提示だけで始められる」の判定に被験者が要る**（根の 7-2）。
   確保できない場合の代替が無い

3. ~~狭い画面で操作の提示が消える~~ → **解決済み。**`shell` が**どの幅でも隠さない**と凍結した
   （`shell@2026-09-05-decision-3`）。幅が足りなければ折り返す

4. ~~`s1` の操作割当を `screens` が写すだけ、という構造が実装に無い~~ → **所有者は確定した。**
   **文字列を生成するのは `screens` だけ**（`frame` の親に残すもの6）。
   **`shell` は場所だけ用意する。**
   キー割り当ての値そのものは `avatar` が持ち、**`s1.controls` で運ぶ。**
   実装は `screens` 相当のコードへ直書きしているので、**そこを `s1` 経由へ変える**
